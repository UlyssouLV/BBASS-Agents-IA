# V1.1.2 — Pièces jointes

## Problem Statement

Le schéma de données de la [1.1.1](v1.1.1-persistance-conversations.md) réserve déjà une table `PieceJointe` (`id`, `message_id`, `nom_fichier`, `type_mime`, `date_creation`), mais elle n'est ni peuplée ni lue par du code applicatif. Un collaborateur ne peut donc joindre aucun document à un message : impossible de faire analyser un PDF, un scan, un tableau Excel ou un document Word par l'IA sans en recopier le contenu à la main dans le chat — impraticable pour un document long, et destructeur pour tout ce qui a une structure (tableaux, mise en forme).

## Solution

Le poste gagne une zone de dépôt minimale (non stylisée — le style est le sujet de la 1.2.0) pour joindre un fichier à un message. Une seule pièce jointe par message pour cette version ; plusieurs pièces jointes, et un traitement spécifique par pôle une fois les Agents métiers construits (1.3.0+), sont des évolutions prévues mais pas construites ici — le schéma ne doit rien fermer qui les empêcherait.

**Jamais la Files API Mistral — le fichier, lui, est bien envoyé à Mistral quand le traitement l'exige.** Pour le PDF et l'image, il n'existe pas de moyen d'obtenir l'OCR ou l'analyse visuelle sans transmettre le fichier à Mistral : ce n'est donc pas ce point-là qui est écarté. Ce qu'on écarte, c'est la **Files API** (upload persistant, référencé ensuite par `file_id`, qui stocke le fichier chez Mistral jusqu'à suppression explicite, structurellement hors ZDR) — le même problème d'isolation déjà écarté pour l'API Agents & Conversations en 1.1.1 (clé API unique partagée par tout le cabinet, aucune notion de sous-compte côté Mistral). À la place, chaque pièce jointe passe par un pipeline d'extraction avant tout appel de chat, propre à son format, avec des appels ponctuels (stateless) plutôt qu'un upload durable :

- **PDF** → endpoint `/v1/ocr` de Mistral (appel stateless, *éligible* ZDR — voir nuance ci-dessous), modèle dédié `mistral-ocr-latest` (différent de `mistral-small-latest` utilisé pour le chat — forme de requête/réponse différente, pas un simple changement de paramètre) → texte/markdown extrait. Le fichier est transmis à cet appel, mais jamais stocké au-delà via la Files API.
- **Word (.docx)** → extraction de texte locale, côté VM centrale (`python-docx`) : seul format qui n'est jamais transmis à Mistral, le fichier ni son contenu brut ne quittent la VM centrale avant l'appel de chat (qui ne reçoit que le texte déjà extrait).
- **Excel (.xlsx)** → extraction locale des valeurs/cellules (`openpyxl`) en texte/tableau, même logique que Word — un tableur est une donnée déjà structurée, pas un document à scanner.
- **Image** → seul cas où aucune alternative locale fiable n'existe : appel vision Mistral (`document_url`/`image_url` en chat completions), avec le fichier transmis. **Compromis assumé et documenté** : ce chemin est structurellement **exclu** du ZDR (pas seulement « pas actif par défaut » comme l'OCR — Mistral l'exclut catégoriquement des fonctionnalités éligibles, voir nuance ci-dessous), contrairement aux trois précédents. En cas d'échec d'analyse (rien d'exploitable dans l'image), le résultat stocké est une explication textuelle de l'échec, pas une erreur HTTP — l'IA doit pouvoir en informer le collaborateur dans sa réponse.

**Nuance importante sur le Zero Data Retention** : contrairement à ce qu'une première lecture pourrait laisser penser, le ZDR n'est **jamais actif par défaut**, y compris pour l'OCR. C'est une option à **demander explicitement** au support Mistral (facturation à l'usage uniquement, approbation à leur discrétion) — voir Further Notes. Tant que cette demande n'est pas faite et approuvée pour le compte Mistral du cabinet, l'OCR et le chat restent des appels stateless mais **retenus** par Mistral pour une durée par défaut non documentée précisément (à vérifier, même caveat que les limites de débit). Le chemin vision (image), lui, reste hors ZDR quoi qu'il arrive.

Le pipeline vit dans un module utilitaire séparé (`vm_centrale/analyse_pieces_jointes/`, un sous-module par format), pensé comme la première brique d'une zone d'utilitaires partagée que les futurs Agents IA par pôle (1.3.0+) réutiliseront — sans construire l'orchestration multi-agents elle-même, qui n'a de sens qu'une fois plusieurs Agents réels à orchestrer.

**Stockage.** Le fichier original (binaire) va sur disque — Postgres n'est pas fait pour de gros blobs, et ce choix anticipe les futurs fichiers volumineux (nuages de points DAO/Topo, potentiellement plusieurs Go, à segmenter côté cabinet plus tard). Racine configurable par `VM_CENTRALE_PIECES_JOINTES_DIR` (même convention que `DATABASE_URL`), chemin `<identifiant_compte>/<conversation_id>/<piece_jointe_id>-<nom_fichier>`. Le contenu extrait (texte) reste en base, sur `PieceJointe`, comme `resume_contexte`/`profil_travail` aujourd'hui. Limite fixe de 20 Mo par fichier, en dur dans le code (comme la fenêtre de 3 messages en 1.1.1), indépendante des plafonds propres à Mistral (20 Mo pour `document_url` inline, 50 Mo/1000 pages pour l'OCR).

**Flux d'upload, en deux temps.** `POST /conversations/{id}/pieces-jointes` (multipart, un seul fichier) : vérifie la propriété de la conversation, fait tourner le pipeline d'extraction, stocke le fichier sur disque et le résultat en base, renvoie `piece_jointe_id`. Pour joindre un fichier dès le tout premier message d'une conversation — qui n'existe pas encore au moment où il faut téléverser le fichier — `POST /pieces-jointes` (sans conversation dans l'URL) offre le même flux, sans conversation à posséder. Les endpoints existants `POST /conversations` et `POST /conversations/{id}/messages` restent en JSON, avec un champ optionnel `piece_jointe_id` : s'il est fourni, le contenu extrait est injecté comme message `system` supplémentaire dans cet appel de chat précis (même mécanisme que `resume_contexte`/`profil_travail`), la pièce jointe est rattachée à la conversation si elle ne l'était pas déjà, puis `PieceJointe.message_id` est renseigné une fois le `Message` créé.

**Résumé glissant.** Quand un message porteur d'une pièce jointe sort de la fenêtre des 3 derniers messages, le résumé glissant n'absorbe pas le contenu complet — seulement une mention courte (une ligne, façon description de skill : juste assez pour situer le sujet). L'appel résumé+profil reçoit un extrait court du contenu (pas son intégralité) pour produire cette mention de façon pertinente plutôt que le seul nom de fichier.

**Tool calling — nouveauté technique de cette version.** Un outil `obtenir_contenu_piece_jointe(piece_jointe_id)` est déclaré sur l'appel de chat principal (jamais sur le titrage ni le résumé+profil), uniquement quand la conversation a au moins une pièce jointe sortie de la fenêtre. Si l'IA en a besoin pour répondre précisément à une question qui s'y réfère, elle appelle l'outil ; le backend résout l'appel (vérifie que la pièce jointe appartient bien à la conversation), va chercher le contenu déjà extrait en base — jamais de ré-analyse — et relance un second appel Mistral avec ce contenu injecté comme message `tool`, pour produire la réponse finale. Tout ça invisible pour le compte, qui ne voit que la réponse. `MistralClient` est étendu pour porter un paramètre `tools` et gérer ce second aller-retour.

**Confidentialité**, identique au régime déjà en place pour les conversations : seul le compte propriétaire de la conversation peut uploader/consulter une pièce jointe (404, jamais 403, y compris pour un compte administrateur). Tous les comptes/pôles peuvent joindre un fichier, sans restriction — aucun Agent métier n'existe encore pour justifier une segmentation.

**Suppression.** La suppression d'une conversation supprime en cascade ses pièces jointes, en base **et** leur fichier physique sur disque — pas de fichier orphelin. (Conserver une pièce jointe au-delà de sa conversation, pour un usage multi-conversationnel ou pour alimenter les futurs Agents, est une piste future, pas construite ici.)

**Sens.** Uniquement l'upload collaborateur → Mistral. Un fichier produit par l'IA en retour est hors périmètre.

## User Stories

1. En tant que collaborateur, je veux pouvoir joindre un fichier (PDF, Word, Excel ou image) à un message depuis une zone de dépôt dédiée du chat, afin que l'IA en tienne compte sans que j'aie à recopier son contenu à la main.
2. En tant que collaborateur, je veux que l'IA me dise clairement qu'elle n'a pas compris une pièce jointe (ex. une image ambiguë) plutôt que de l'ignorer silencieusement, afin de savoir s'il faut que je fournisse l'information autrement.
3. En tant que collaborateur, je n'ai rien à faire de particulier si l'IA a besoin de revenir sur le contenu complet d'une pièce jointe plus tard dans la conversation : elle le redemande elle-même, de façon invisible pour moi.
4. En tant que collaborateur, je veux qu'une pièce jointe que j'ai envoyée reste strictement privée à ma conversation, inaccessible à tout autre compte y compris un compte administrateur.
5. En tant que collaborateur, je veux que la suppression d'une conversation supprime aussi ses pièces jointes (fichier compris), afin de ne rien laisser traîner.
6. En tant que responsable du projet, je veux que le contenu d'un document envoyé à Mistral ne dépende jamais de son stockage propre au-delà de l'appel ponctuel strictement nécessaire, afin de garder la même maîtrise de confidentialité déjà actée pour les conversations (1.1.1).
7. En tant que responsable du projet, j'accepte explicitement qu'une image — seul format sans alternative locale d'analyse — passe par un appel Mistral où le Zero Data Retention est structurellement indisponible (contrairement à l'OCR, où il est possible mais pas automatique), tant que ce compromis reste documenté et isolé aux images.
8. En tant que responsable du projet, je veux qu'une seule pièce jointe soit acceptée par message pour ce premier livrable, sachant que plusieurs pièces jointes et un traitement spécifique par pôle des futurs Agents IA sont prévus pour une version ultérieure.
9. En tant que futur mainteneur, je veux que le pipeline d'analyse de pièces jointes vive dans un module utilitaire séparé et clair, afin de le réutiliser et l'étendre pour les futurs Agents IA par pôle (1.3.0+) sans redécouper l'existant.
10. En tant que futur mainteneur, je veux que le coût en tokens reste maîtrisé : le résumé glissant ne garde qu'une mention courte d'une pièce jointe une fois sortie de la fenêtre des derniers messages, jamais son contenu intégral.
11. En tant que développeur, je veux une limite de taille fixe et documentée (20 Mo) par pièce jointe, indépendante des plafonds propres à Mistral, afin de protéger le stockage et les temps d'upload.
12. En tant que développeur, je veux que le fichier original soit stocké sur disque plutôt qu'en base, afin de ne pas dégrader Postgres avec de gros blobs et d'anticiper les futurs fichiers volumineux (nuages de points DAO/Topo).

## Implementation Decisions

- **`PieceJointe` (VM centrale), schéma étendu** : `id`, `identifiant_compte` (nouvelle colonne, toujours renseignée à l'upload — seule façon de vérifier la propriété d'une pièce jointe pas encore rattachée à une conversation, voir `conversation_id`), `conversation_id` (FK `Conversation`, nouvelle colonne, **nullable** — voir ci-dessous), `message_id` (FK `Message`, devient **nullable** — renseigné seulement une fois la pièce jointe liée à un message envoyé), `nom_fichier`, `type_mime`, `taille_octets` (nouvelle colonne), `chemin_fichier` (nouvelle colonne, chemin relatif sous `VM_CENTRALE_PIECES_JOINTES_DIR`), `contenu_extrait` (nouvelle colonne texte — contenu extrait, ou explication d'échec le cas échéant), `echec_analyse` (nouvelle colonne booléenne), `date_creation`. Création via `Base.metadata.create_all`, pas de migration (même convention qu'avant).
- **`POST /conversations/{conversation_id}/pieces-jointes`** (multipart, un seul fichier) : authentifié par jeton, vérifie la propriété de la conversation (`_recuperer_conversation_du_compte`, 404 sinon). Refuse (400) tout fichier > 20 Mo ou d'un type non supporté (PDF, `.docx`, `.xlsx`, images). Insère la ligne `PieceJointe` (`db.flush()` pour obtenir l'id, même pattern que `creer_conversation`), écrit le fichier sur disque au chemin `<identifiant_compte>/<conversation_id>/<piece_jointe_id>-<nom_fichier>`, exécute le pipeline d'extraction adapté au type, met à jour `contenu_extrait`/`echec_analyse`, commit. Renvoie `{piece_jointe: {id, nom_fichier, type_mime}, echec_analyse}`.
- **`POST /pieces-jointes`** (multipart, sans `conversation_id` dans l'URL) : même comportement que ci-dessus (mêmes validations, même pipeline d'extraction, même réponse), mais `conversation_id` reste `None` à l'écriture — le fichier est déposé sous `<identifiant_compte>/_sans_conversation/<piece_jointe_id>-<nom_fichier>` en attendant son rattachement. **Nécessaire pour référencer une pièce jointe dès le tout premier message d'une conversation** (ticket #45) : `POST /conversations/{conversation_id}/pieces-jointes` exige une conversation déjà existante, alors que `POST /conversations` crée la conversation en même temps que ce premier message — sans ce point d'entrée, aucune pièce jointe ne pourrait jamais exister avant la conversation qui la référence dès sa création.
- **Module `vm_centrale/analyse_pieces_jointes/`** : un point d'entrée `analyser(fichier, type_mime) -> ResultatAnalyse` qui route vers le bon sous-module (OCR Mistral pour PDF, `python-docx` pour Word, `openpyxl` pour Excel, appel vision Mistral pour image), pensé comme premier utilitaire réutilisable, pas comme logique interne au routeur `conversations.py`.
- **Tags de modèle centralisés** : `vm_centrale/config.py` porte désormais `MODELE_CHAT = "mistral-small-latest"` et `MODELE_OCR = "mistral-ocr-latest"` (constantes nommées par fonction, pas par valeur) — tout code appelant Mistral (chat, titrage, résumé+profil, vision image, OCR) référence l'une de ces constantes plutôt qu'une chaîne en dur, pour qu'un changement de modèle futur (par fonction) se fasse à un seul endroit. `MistralClient` gagne une méthode `.ocr(document)` dédiée (requête/réponse `/v1/ocr`, distincte de `.chat()` qui reste sur `/v1/chat/completions`).
- **`ConversationCreeRequest` / `MessageEnvoyeRequest`** : nouveau champ optionnel `piece_jointe_id: int | None`. À l'envoi : vérifie que la pièce jointe appartient au compte et (si déjà rattachée) à cette conversation précise, et n'est pas déjà liée à un message (404/400 sinon) ; injecte `contenu_extrait` comme message `system` supplémentaire pour cet appel précis ; une fois le `Message` persisté, renseigne `PieceJointe.message_id` (et `conversation_id` si elle ne l'était pas déjà — déplace alors le fichier de `_sans_conversation/` vers le chemin canonique). Pour `POST /conversations`, la conversation est créée et *flushée* (jamais commitée) avant l'appel Mistral, pour connaître son id au moment de valider/rattacher la pièce jointe ; un échec de l'appel Mistral déclenche un rollback explicite (pas de conversation fantôme persistée, même garantie qu'avant).
- **Résumé + profil (`_prompt_resume_et_profil`)** : quand un message sortant de la fenêtre porte une pièce jointe, le prompt inclut un extrait court de `contenu_extrait` (pas son intégralité) en plus du message, pour que `resume_contexte` en tire une mention courte et pertinente plutôt qu'un simple nom de fichier.
- **Tool calling** : `MistralClient` étendu pour accepter un paramètre `tools` optionnel et détecter une réponse de type appel d'outil (plutôt qu'un contenu texte final). Un outil `obtenir_contenu_piece_jointe(piece_jointe_id: int)` est déclaré uniquement dans l'appel de réponse de chat principal (`_appeler_reponse_chat`), et seulement si la conversation a au moins une `PieceJointe` liée (`message_id` non nul) dont le message n'est plus dans `derniers_messages`. Si Mistral répond par un appel d'outil : le backend résout `piece_jointe_id` (vérifie l'appartenance à la conversation), récupère `contenu_extrait` déjà en base, relance un appel avec un message `role: tool` portant ce contenu, et utilise la réponse de ce second appel comme réponse finale.
- **Tool calling, précision post-livraison (#50)** : l'essai fonctionnel du 17/09/2026 (`docs/suivi-avancement/essai-pj-2026-09-17.md`) a montré que l'IA ne retrouve pas fiablement la bonne pièce jointe une fois hors fenêtre, faute d'indice pour choisir entre plusieurs `piece_jointe_id`. La description de l'outil, générée à chaque appel (jamais une liste figée dans le schéma déclaré une fois pour toutes), doit énumérer les pièces jointes éligibles de la conversation avec leur nom de fichier en face de leur id. Ne change ni le nombre d'outils déclarés (toujours un seul) ni la condition de déclenchement (toujours : au moins une pièce jointe hors fenêtre).
- **Message système d'une pièce jointe, précision post-livraison (#50)** : `_message_systeme_piece_jointe` doit indiquer explicitement que le fichier injecté est celui du message du tour en cours, pas un exemple ou le rappel d'un tour antérieur — l'essai a montré le modèle traiter un extrait vision comme un cas passé plutôt que comme la pièce jointe du message courant. Ne change ni le moment d'injection (un seul tour, cf. Résumé glissant ci-dessus) ni son contenu (toujours `contenu_extrait` intégral pour ce tour précis).
- **Résumé + profil, garde-fou post-livraison (#50)** : `_prompt_resume_et_profil` doit exclure explicitement du `profil_travail_delta` tout trait décrivant le comportement de l'assistant lui-même (ton, réflexes propres) plutôt qu'une caractéristique observée chez le compte, pour éviter que le profil ne s'auto-renforce sur les tics de l'IA (ton coach, suggestions d'outils externes constatées dans l'essai).
- **Suppression** (`supprimer_conversation`) : supprime les lignes `PieceJointe` de la conversation et leur fichier physique (`os.remove` sur `chemin_fichier`, avant la suppression des messages/conversation), même transaction.
- **Config** : nouvelle variable d'environnement `VM_CENTRALE_PIECES_JOINTES_DIR` (racine du stockage fichier), même convention que `DATABASE_URL`.
- **Jamais** d'appel à la Files API Mistral, jamais de fichier brut transmis dans un message de chat.

## Testing Decisions

Même convention que V1/V1.1/V1.1.1 : tests à la frontière HTTP, sur des réponses observables, jamais sur des appels de fonction interne.

- `POST /conversations/{id}/pieces-jointes` : 201 avec un fichier PDF/Word/Excel/image valide (extracteurs et appels Mistral mockés), renvoie `piece_jointe_id` ; le fichier existe bien sur disque au chemin attendu après l'appel ; 404 sur une conversation d'un autre compte ; 400 sur un fichier > 20 Mo ou d'un type non supporté ; une image dont l'analyse échoue (mock) renvoie 201 avec `echec_analyse: true`, pas une erreur HTTP.
- `POST /pieces-jointes` : 201, `conversation_id` reste `None` en base ; 401 sans jeton ; mêmes validations 400 que ci-dessus.
- `POST /conversations` / `POST /conversations/{id}/messages` avec `piece_jointe_id` : le contenu extrait apparaît dans les messages envoyés au client Mistral mocké pour cet appel (vérifié sur les arguments passés) ; `PieceJointe.message_id` est renseigné après succès, et `conversation_id` si elle ne l'était pas déjà (fichier déplacé au chemin canonique) ; 404/400 si le `piece_jointe_id` n'appartient pas au compte ou à cette conversation, ou est déjà lié à un autre message ; échec de l'appel Mistral ne rattache pas la pièce jointe (rollback).
- Résumé glissant : une fois qu'un message avec pièce jointe sort de la fenêtre, `Conversation.resume_contexte` contient une mention (mock configuré pour le vérifier), sans que l'intégralité de `contenu_extrait` soit passée dans les arguments de l'appel resume+profil mocké.
- Tool calling : avec une pièce jointe hors fenêtre, l'appel Mistral mocké reçoit bien un paramètre `tools` non vide ; quand le mock renvoie un appel d'outil, un second appel Mistral mocké a lieu avec le contenu de la pièce jointe injecté, et c'est la réponse de ce second appel qui est renvoyée au client.
- `DELETE /conversations/{id}` : les lignes `PieceJointe` de la conversation disparaissent de la base, et leur fichier n'existe plus sur le système de fichiers (vérifié directement, pas seulement en base).
- Confidentialité : 404 (jamais 403) sur toute tentative d'upload ou de référence à une pièce jointe d'une conversation appartenant à un autre compte, y compris avec un jeton `est_admin = true`.
- Post-livraison (#50) : avec deux pièces jointes hors fenêtre, le paramètre `tools` transmis au client Mistral mocké mentionne le nom de fichier de chacune (vérifié sur les arguments passés), pas seulement leurs ids ; le message système injecté pour la pièce jointe du tour précise qu'il s'agit du fichier du message courant ; le prompt résumé+profil contient une consigne explicite excluant les traits de comportement de l'assistant du `profil_travail_delta` (test sur la construction du prompt, pas sur ce qu'un vrai modèle Mistral en ferait — hors de portée d'un test mocké).

## Out of Scope

- Plusieurs pièces jointes par message (une seule pour cette version).
- Traitement de pièce jointe spécifique par pôle/Agent métier (aucun Agent construit avant 1.3.0).
- Conservation d'une pièce jointe au-delà de la conversation/du message qui la porte ; pas de zone de pièces jointes par compte ni de réutilisation multi-conversationnelle.
- Formats autres que PDF/Word/Excel/images (PowerPoint, ODT, fichiers CAO, nuages de points…).
- Fichiers produits par l'IA en retour (uniquement upload collaborateur → Mistral).
- Interface stylisée d'upload — zone fonctionnelle minimale seulement, le style est le sujet de 1.2.0.
- Limite de taille/formats configurables — fixés en dur pour cette version, comme la fenêtre de 3 messages en 1.1.1.
- Orchestration générique multi-agents/multi-outils — un seul outil pour cette version ; le cadre générique attendra plusieurs Agents réels en 1.3.0+.
- Déploiement sur la vraie VM centrale (toujours pas créée) — stockage fichier local/volume Docker en attendant.

## Further Notes

- Vocabulaire : voir `CONTEXT.md` (`Pièce jointe`, `Conversation`, `Agent`, `Pôle`) et `docs/adr/0002`, `docs/adr/0009`.
- Recherche Mistral (docs.mistral.ai) : `document_url` en chat completions accepte une URL publique ou un base64 inline (limite ~20 Mo pour le contenu du message), supporte nativement `mistral-small-latest` (déjà le modèle utilisé pour le chat, pas de changement de modèle nécessaire pour la vision) — docs.mistral.ai/studio-api/document-processing/document_qna, docs.mistral.ai/capabilities/document_ai/document_qna. Endpoint OCR dédié (`/v1/ocr`), stateless, jusqu'à 50 Mo / 1000 pages, modèle `mistral-ocr-latest` — docs.mistral.ai/api/endpoint/ocr. Function/tool calling documenté, standard chez tous les fournisseurs sérieux depuis 2023 — docs.mistral.ai/studio/conversations/function-calling.
- **Zero Data Retention, précisément** (docs.mistral.ai/admin/monitor-comply/zero-data-retention, help.mistral.ai/en/articles/347612) : **jamais actif par défaut**, pour aucun appel — c'est une option à activer explicitement, disponible uniquement en facturation à l'usage (« pay-as-you-go »), sur demande motivée auprès du support Mistral, approuvée à leur discrétion (visible ensuite dans le panneau Admin, Privacy settings). Une fois activée, elle couvre les appels stateless éligibles : chat completions texte, **OCR inclus**. Elle est en revanche **structurellement exclue** (pas juste « à activer ») pour tout ce qui relève de la vision (`document_url`/`image_url` en chat direct, « Document QnA »/Annotation) et pour la Files API (explicitement stateful, fichiers conservés jusqu'à suppression). **Action de suivi hors de ce projet logiciel** : quelqu'un ayant accès au compte Mistral du cabinet devrait faire la demande d'activation ZDR pour que le chat et l'OCR en bénéficient réellement ; tant que ce n'est pas fait, ces appels restent stateless mais retenus par Mistral pour une durée par défaut non documentée précisément dans les sources consultées.
- **Choix OCR-puis-texte plutôt que vision directe pour PDF/scans** : garde tout le pipeline dans les appels Mistral au moins *éligibles* ZDR (à défaut d'être ZDR tant que la demande ci-dessus n'est pas faite), cohérent avec la position déjà prise en 1.1.1. Seule l'image force le chemin vision (pas d'alternative locale, et structurellement hors ZDR même après activation), compromis assumé explicitement (voir User Story 7).
- **Rate limits Mistral** réels non vérifiés dans cette recherche (même caveat que 1.1.1) : dépendent du palier du compte Mistral du cabinet.
- Idées explicitement mises de côté pour une version future, à ne pas perdre : plusieurs pièces jointes + traitement par pôle des futurs Agents ; conservation de pièces jointes au-delà d'une conversation pour usage multi-conversationnel/entraînement des Agents ; segmentation de fichiers volumineux (nuages de points DAO/Topo) via le futur module utilitaire.
