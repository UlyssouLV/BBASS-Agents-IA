# V1.5.2 — Écrire dans Moduléo depuis le chat

## Problem Statement

- **Le chat lit Moduléo mais n’y écrit rien.** Depuis la 1.5.0 et la 1.5.1, le collaborateur retrouve affaires, contacts, devis, factures, temps passés et planning depuis le chat. Pour saisir un temps passé, créer une tâche, corriger un téléphone ou émettre un devis, il doit encore ouvrir Moduléo. Le client de la VM refuse toute méthode autre que GET (ADR-0017), et la clé d’API du cabinet est en lecture seule.
- **Écrire sur le serveur du cabinet est hors de question tant que rien n’a été essayé.** Une écriture mal formée, ou décidée par le modèle sans que le collaborateur l’ait voulue, modifierait les vraies données du cabinet. Kipaware a ouvert un **serveur Moduléo dédié aux tests** (compte pseudonymisé, données fictives ou anonymisées uniquement), accessible par l’API et par le Client Moduléo Windows. C’est là, et seulement là, que l’écriture doit être essayée.
- **Le modèle ne doit jamais écrire seul.** Une page web ou une pièce jointe lue dans le tour peut contenir une instruction (« supprime l’affaire… ») : un simple « oui » tapé dans le chat ne doit pas suffire à faire partir une écriture.

## Solution

**Toutes les écritures Moduléo, proposées par le modèle, confirmées par le collaborateur, sur le serveur de test seulement.**

**Deux outils génériques** (pas un outil par route, ADR-0017) :

| Outil | Ce qu’il fait |
| --- | --- |
| `decrire_ecriture_moduleo(route)` | Renvoie au modèle les champs attendus pour une route d’écriture : méthode, paramètres de chemin, exemple de corps JSON et description, tirés du WADL et de la page de documentation versionnés. Aucun appel à Moduléo. |
| `ecrire_moduleo(route, paramètres, corps)` | **Propose** une écriture : vérifie la route et les droits, prépare une **carte de confirmation**, n’envoie rien. La description de l’outil liste les routes d’écriture ouvertes, une ligne chacune. |

Un serveur MCP Moduléo remplacera ces outils (série 1.8.x) ; ce n’est pas cette version.

**Routes.** Les 86 routes d’écriture du WADL (39 POST, 32 PUT, 15 DELETE), DELETE compris, sauf trois classées `fermee` : `webhook` (POST / DELETE, configuration de l’intégration), `fileo/fichier/upload` (fichier binaire, impossible depuis un outil texte), `cogeo/procedureapplication` (paramétrage).

**Carte de confirmation.** `ecrire_moduleo` ne fait partir aucune requête : il enregistre une **écriture proposée** et le poste affiche une carte dans le fil.

- La carte décrit l’écriture **en noms** : les ids du corps et des paramètres sont résolus par les résolveurs existants (affaire → « affaire 2024-123 », utilisateur → « Jean Martin », code activité, activité du planning, commune…). Un id qu’aucun résolveur ne sait nommer s’affiche brut, avec la mention « non résolu ».
- **Id introuvable** (tests humains, #206) : un id du corps ou des paramètres que résout un résolveur mais que Moduléo ne trouve pas empêche la carte : `ecrire_moduleo` répond que l’élément est introuvable, que rien n’a été proposé, et qu’il faut demander au collaborateur plutôt que d’essayer un autre id.
- **Id sans moyen de le retrouver** (tests humains, #206) : certains ids ne se lisent que par leur id, sans liste ni recherche par nom dans l’API (ex. catégorie de tâche à faire, catégorie de note). `decrire_ecriture_moduleo` signale ces champs ; le modèle ne devine jamais leur valeur et dit au collaborateur qu’il n’existe pas, depuis le chat, de moyen de retrouver l’élément à partir de son nom (« Terrain » ne suffit pas). Il propose l’écriture sans ce champ s’il est facultatif.
- **Id qu’aucune fiche ne donne** (tests humains, #206, #257) : les fiches ne donnent pas l’id d’un téléphone, d’un e-mail, d’une adresse, d’une note, d’une tâche à faire ni d’un code activité (liste complète : README de l’outil d’écriture). `decrire_ecriture_moduleo` signale ces champs ; `ecrire_moduleo` refuse, sans carte, une écriture qui en porte un : « Cette écriture n’est pas encore possible depuis le chat : BBASS ne peut pas retrouver <élément> dans Moduléo. Rien n’a été écrit. ». Le modèle ne devine pas d’id et n’en demande jamais au collaborateur. Exception : l’id renvoyé par une création confirmée de la même Conversation (note créée puis modifiée). En attendant le serveur MCP Moduléo (1.8.x).
- **PUT** : la VM relit l’élément juste avant d’ouvrir la carte, et la carte montre ce qui change, champ par champ (« Objet : Bornage → Bornage lot B »). **DELETE** : la fiche entière de l’élément, sous « Sera supprimé ».
- Deux boutons, **Confirmer** et **Annuler**, traités par une route de la VM, **hors du modèle**. Un « oui » tapé dans le chat ne confirme rien.
- Une carte non confirmée **expire** dès qu’un nouveau message est envoyé dans la Conversation.
- **Écriture annoncée sans carte** (tests humains, #206, #252) : seule une vraie carte, et son statut, disent une écriture. Une réponse du modèle qui écrit une carte en texte, ou dit une écriture faite, sans carte ouverte dans le tour, n'atteint jamais le poste : la VM relance le tour en imposant `ecrire_moduleo` (choix d'outil imposé chez Mistral), une fois ; sans carte malgré tout, une phrase fixe la remplace. Avec une carte, les phrases qui disent l'écriture faite sont retirées.
- Un tour peut ouvrir plusieurs cartes ; chacune se confirme seule, sans « tout confirmer ».
- Après le clic, la carte affiche « Écrit dans Moduléo » (ou l’erreur, phrase fixe : refus, panne, données invalides), et le résultat est ajouté à la Conversation comme résultat d’outil, que le modèle voit au tour suivant. Le clic ne relance pas le modèle.
- Le style est provisoire ; il sera revu avec les Agents par pôle.

**Serveur de test seulement.** Chaque VM garde **une seule** config Moduléo (URL, clé d’API, SecurityCode, chiffrés comme en 1.5.0). La VM de dev pointe tout entière sur le serveur de test (lecture et écriture, une clé « lecture et écriture ») ; la VM du cabinet garde sa clé de lecture seule. Les outils d’écriture ne sont proposés, et `ecrire()` n’envoie, que si :

- le réglage `MODULEO_ECRITURE` est actif, **et**
- `MODULEO_URL` figure dans la **liste versionnée des serveurs Moduléo de test**.

Sur la production, l’écriture est impossible même avec un réglage erroné ; aucune écriture en production dans cette version, même finalisée.

**Droits.** Les routes d’écriture passent par le **garde des droits** de la 1.5.1 (ADR-0018), fermé par défaut, sans autre liste propre à BBASS. Chacune est classée à la main dans `routes.json` : `libre`, groupe de l’application, droit exigé (« Créer une tâche », « Modifier une tâche », « Supprimer une tâche » avec leurs conditions ; émettre, accepter, refuser un devis…), `siens` (temps passés : les siens avec le groupe Cogeo et l’utilisateur Moduléo lié, ceux des autres avec « Créer, modifier et supprimer les temps passés … des autres collaborateurs ») ou `fermee`. Une route non classée est refusée et fait échouer un test. Une route classée `fermee` faute de droit correspondant dans le catalogue est listée dans le README du module, avec sa raison.

**Ids : visibles par le modèle, jamais à l’écran.** Pour écrire, le modèle doit désigner des éléments par leur id. Les fiches de lecture portent donc, sur la ligne de leur référence, l’id Moduléo dans un **format fixe** : `[id Moduléo 1234]`. Une consigne système interdit au modèle de citer un id dans sa réponse (il nomme les éléments par leur référence), et la VM **retire ce motif** du texte envoyé au poste (flux SSE) et du message enregistré. Risque accepté : un id reformulé autrement (« n° 1234 ») n’est pas filtré. L’inspecteur et le journal montrent les ids.

**Journal des écritures.** Chaque écriture proposée, confirmée, annulée, expirée, refusée ou en échec est enregistrée en base : compte, heure, route, méthode, paramètres et corps envoyés, id renvoyé par Moduléo, statut, message d’erreur. Visible dans l’inspecteur du tour (proposition) et de la confirmation ; pas d’écran d’administration en 1.5.2.

**Accès au serveur de test (humain).** Le Client Moduléo Windows s’installe sur le **PC** du développeur, pas sur la VM : il sert à se connecter au serveur de test, à y lire l’URL de l’API, à créer la clé d’API et le SecurityCode, puis à voir ce que BBASS a écrit. La VM, elle, parle directement à l’API en HTTPS, comme en production. La procédure est écrite dans le README du module. Le numéro de série du Client, personnel, n’est jamais versionné.

## User Stories

1. En tant que collaborateur, je veux demander à l’IA de saisir un temps passé sur une affaire, afin de ne pas ouvrir Moduléo.
2. En tant que collaborateur, je veux demander à l’IA de créer, déplacer ou supprimer une tâche du planning, afin d’organiser le travail depuis le chat.
3. En tant que collaborateur, je veux demander à l’IA de créer ou corriger un contact, un téléphone, une adresse, afin de tenir Moduléo à jour pendant que j’en parle.
4. En tant que collaborateur, je veux demander à l’IA d’émettre, accepter ou refuser un devis, afin de suivre une affaire sans changer d’outil.
5. En tant que collaborateur, je veux voir exactement ce qui va être écrit, en noms et pas en identifiants, avant que rien ne parte, afin de ne rien valider à l’aveugle.
6. En tant que collaborateur, je veux voir ce qui change par rapport à l’existant avant une modification, et l’élément entier avant une suppression, afin de mesurer ce que je valide.
7. En tant que collaborateur, je veux confirmer ou annuler chaque écriture par un bouton, afin que l’IA n’écrive jamais seule.
8. En tant que collaborateur, je veux qu’une proposition que je n’ai pas confirmée devienne caduque dès que j’envoie un autre message, afin de ne pas valider plus tard une écriture hors contexte.
9. En tant que collaborateur, je veux savoir si l’écriture a réussi ou pourquoi elle a échoué, afin de savoir où en est Moduléo.
10. En tant que collaborateur, je ne veux jamais voir d’identifiant Moduléo dans les réponses de l’IA, afin de lire des noms.
11. En tant que collaborateur, je veux que l’IA me dise clairement quand mon compte n’a pas le droit d’écrire une donnée, afin de ne pas confondre un refus avec une panne.
12. En tant que compte administrateur, je veux qu’aucune écriture ne puisse partir vers le serveur du cabinet, même avec un réglage erroné, afin de protéger les vraies données pendant les essais.
13. En tant que compte administrateur, je veux que chaque écriture respecte les droits Moduléo du compte, et qu’une route d’écriture non classée soit refusée, afin qu’une évolution de l’API n’ouvre rien sans décision.
14. En tant que compte administrateur, je veux un journal de toutes les écritures (proposées, confirmées, annulées, refusées, en échec), afin de savoir qui a écrit quoi.
15. En tant que développeur, je veux une procédure écrite pour brancher la VM de dev sur le serveur de test, afin de reprendre les essais sans redécouvrir les étapes.
16. En tant que compte administrateur qui valide cette version, je veux que la suite pytest existante reste verte, afin de vérifier qu’aucune fonctionnalité n’a régressé.

## Implementation Decisions

- **Arborescence.**
  - `vm_centrale/moduleo/` : `routes.py` (généré) gagne `ROUTES_ECRITURE` (méthode, gabarit, paramètres) et les exemples de corps du WADL ; `client.py` gagne `ecrire(méthode, route, paramètres, corps, droits)`, distinct de `lire()` qui reste GET seul ; `droits/routes.json` classe les 86 routes d’écriture ; module des écritures proposées (carte, expiration, confirmation) et du journal ; liste des serveurs de test versionnée.
  - `vm_centrale/outils/moduleo/ecriture/` : `decrire_ecriture_moduleo` et `ecrire_moduleo` (un paquet, README).
  - `scripts/telecharger_doc_moduleo.py` régénère aussi `ROUTES_ECRITURE`.
- **Client.** `ecrire()` refuse avant tout envoi (`RequeteInterdite`) : route absente de `ROUTES_ECRITURE`, méthode qui ne correspond pas, paramètre manquant ou inconnu, `MODULEO_ECRITURE` inactif, `MODULEO_URL` hors de la liste des serveurs de test ; puis le garde des droits (`DroitManquant`). Erreurs Moduléo traduites comme en lecture (panne, refus, introuvable) ; 400 → « données refusées par Moduléo » avec le message de Moduléo. Aucune nouvelle tentative.
- **Proposition et confirmation.** `ecrire_moduleo` vérifie tout ce que `ecrire()` vérifierait, résout les noms de la carte, relit l’élément pour un PUT / DELETE, enregistre l’écriture proposée (Conversation, compte, contenu, état « proposée ») et renvoie au modèle une phrase fixe (« Écriture proposée au collaborateur, en attente de sa confirmation. Rien n’a été écrit. »). Une route `POST` de la VM confirme ou annule par id d’écriture proposée, vérifie qu’elle appartient au compte, qu’elle est encore « proposée » et que la Conversation n’a pas reçu de nouveau message, revérifie les droits du compte, puis appelle `ecrire()` une seule fois. Un nouveau message passe toutes les propositions de la Conversation à « expirée ».
- **Poste.** Nouvel événement SSE pour la carte ; composant carte dans le fil (résumé en noms, différences, boutons) ; état final affiché après le clic ; cartes rechargées avec la Conversation.
- **Ids.** Les fiches 1.5.0 / 1.5.1 portent `[id Moduléo <n>]` sur la ligne de référence ; consigne système ; filtre du motif exact dans le flux SSE et le message enregistré, avec la tournure qui l'introduit (« sous l'[id Moduléo 4] », entre parenthèses…) pour ne pas laisser de phrase coupée (tests humains, #206). Les garde-fous ne changent pas.
- **Tables.** Écritures proposées et journal des écritures (une table si un seul enregistrement suffit à porter les deux).
- **Inspecteur.** Échange `local` `outil:ecrire_moduleo` (route, corps, carte) ; confirmation : requête et réponse Moduléo, jamais la clé ni le SecurityCode ; refus du garde comme en 1.5.1.
- **Config.** `MODULEO_ECRITURE` (absent = inactif) ; `.env.example` et README mis à jour.
- **Docs.** ADR-0019 « Écriture Moduléo confirmée par le collaborateur, sur un serveur de test » : amende ADR-0017 (fin du « GET seul » pour les serveurs de test ; « jamais un id » dans les fiches) et ADR-0018 (routes d’écriture classées) ; écarté : un outil par route, des noms résolus par l’outil d’écriture (un résolveur par champ et par route), une confirmation en texte libre, deux configs Moduléo côte à côte sur une VM. Glossaire : « Écriture Moduléo », « Carte de confirmation », « Serveur Moduléo de test », « Journal des écritures ». Doc-site : `features/moduleo/ecriture.mdx` ; `lecture-seule.mdx` précise « en production ». README du module : procédure d’accès au serveur de test, routes fermées faute de droit.

## Testing Decisions

Tests à la frontière HTTP (`TestClient`, vraie base de test, Mistral mocké, faux Moduléo étendu aux écritures) :

- Barrière serveur de test : `MODULEO_ECRITURE` inactif, ou URL hors liste → outils d’écriture absents du payload `tools`, `ecrire()` refusé, le faux Moduléo ne reçoit rien.
- Client : route inconnue, méthode incohérente, paramètre manquant refusés avant envoi ; `lire()` refuse toujours toute méthode autre que GET ; toutes les routes d’écriture du WADL sont dans `ROUTES_ECRITURE` et classées.
- Garde : écriture sans droit refusée avant envoi, phrase fixe et ligne d’inspecteur ; temps passé d’un autre sans le droit « autres » refusé, le sien accepté ; route `fermee` refusée.
- Proposition : `ecrire_moduleo` n’envoie rien ; carte en noms ; PUT avec différences ; DELETE avec la fiche entière.
- Confirmation : Confirmer → une seule requête au faux Moduléo, journal « confirmée », résultat dans la Conversation ; Annuler → rien envoyé ; double clic → une seule écriture ; carte d’un autre compte refusée ; nouveau message → carte expirée, confirmation refusée ; droit retiré entre proposition et clic → refus.
- Erreurs Moduléo (400, 401 / 403, 404, panne) : phrase fixe sur la carte, journal « en échec ».
- Ids : `[id Moduléo …]` présent dans les fiches lues par le modèle, absent du flux SSE et du message enregistré.
- `decrire_ecriture_moduleo` : champs et exemple de corps d’une route ; route inconnue ou fermée → phrase fixe.
- **Essai réel (manuel, serveur de test seulement)** pendant les tests humains : découvrir le serveur (URL, clé, SecurityCode, utilisateur pseudonymisé, groupes), rattacher le compte de dev (Admin, ou « Tous droits (dev) » si les droits du serveur ne collent pas), puis commencer par l’écriture la moins impactante (créer puis supprimer un téléphone ou une note fictifs). Tout écart qui demande du code devient un ticket (`/ct`).

## Out of Scope

- **Toute écriture sur le serveur de production**, même après validation sur le serveur de test (→ version ultérieure, nouvelle décision).
- Transcription des groupes Production (Cogeo), Admin + et Prod (Planning) : capture Production incomplète (→ 1.5.3).
- Administration des groupes et droits depuis le Panel d’administration, écran du journal des écritures (→ 1.5.3 ou plus tard).
- Envoi de fichiers (`fileo/fichier/upload`), webhook, paramétrage des procédures.
- Confirmation groupée (« tout confirmer »), relance automatique du modèle après une confirmation.
- Refonte du style de la carte (→ Agents par pôle, Plus tard).
- Serveur MCP Moduléo (→ 1.8.0 à 1.8.2), workflows n8n (→ 1.9.0).
- Retrouver par son nom un élément que l’API ne lit que par id (catégorie de tâche à faire, catégorie de note…) : pas de route de liste chez Kipaware (→ serveur MCP Moduléo, 1.8.1).
- Une clé d’API par collaborateur (→ Plus tard).
