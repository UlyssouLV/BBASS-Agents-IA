# V1.2.0 — Mise à jour de l'interface (poste)

## Problem Statement

Le poste est aujourd'hui une unique page HTML (`poste/src/poste/static/index.html`, 316 lignes) et un unique script (`app.js`, 1277 lignes) en JavaScript nu, sans build, servis tels quels par FastAPI (`StaticFiles`/`FileResponse`). Ça a bien fonctionné pour V1 à 1.1.3, mais l'écran comptes (compte administrateur) le montre à bout de souffle : `<section id="onglet-comptes">` empile, sans aucune modale, le tableau des comptes, le formulaire de modification, le formulaire de création, deux blocs de révélation de mot de passe, un message de déconnexion forcée, et deux formulaires de confirmation par Clé d'administration VM (changement de statut administrateur, suppression) — 127 lignes sur 316, tout affiché en permanence dès que l'onglet est ouvert.

Le problème dépasse le seul écran comptes. Les versions suivantes déjà connues (1.3.0 — premier Agent métier Moduléo, 1.4.0 — pièces jointes multiples et traitement par pôle) et celles au-delà vont ajouter des écrans, pas en retirer. Or la maintenance de ce code ne sera, à terme, plus portée par une personne qualifiée sur place : c'est un agent IA de développement qui continuera à faire évoluer le logiciel, un compte administrateur se contentant de valider les changements (voir la feuille de route, section « Agent IA de continuation du développement »). Un unique fichier JavaScript de plus en plus long, sans filet de type, est le pire terrain pour ça.

## Solution

**Passage à React + TypeScript + Vite.** Le front du poste (connexion, changement de mot de passe, chat, consommation, profil de travail, comptes, consommations administrateur) est entièrement réécrit en React/TypeScript, buildé par Vite. Migration complète en une fois plutôt qu'écran par écran, pour ne pas faire cohabiter deux paradigmes pendant plusieurs versions alors que 1.3.0/1.4.0 vont ajouter des écrans par-dessus.

**shadcn/ui pour les briques d'interface.** Les composants de base (modale/dialog, table, formulaire) viennent de shadcn/ui — copiés dans le repo, pas une dépendance opaque, donc restylables librement. Implique Tailwind CSS. Le plugin Claude `frontend-design` est utilisé pour poser une direction esthétique simple sur ces briques, cohérent avec « simple au début » de la feuille de route.

**TanStack Query pour les appels à la VM centrale.** Remplace les appels `fetch` ad hoc d'`app.js` par des hooks de requête/mutation avec cache et gestion d'erreur standardisée — même contrat HTTP qu'aujourd'hui, aucun endpoint de la VM centrale ne change.

**Pas de routeur.** Le poste reste une appli locale mono-fenêtre (LAN, futur lanceur pywebview) : la navigation entre écrans et entre onglets reste un état React interne, sans URL — même logique qu'aujourd'hui (attribut `hidden` togglé), juste réécrite.

**L'écran comptes devient modal.** Le tableau des comptes reste la vue par défaut ; « Créer un compte », modifier un compte, changer son statut administrateur et le supprimer s'ouvrent chacun dans une modale shadcn/ui dédiée, au lieu d'être des blocs empilés en permanence. La Clé d'administration VM reste exigée dans la modale de suppression et de changement de statut administrateur — aucun changement de sécurité, seulement de présentation.

**Aucun changement côté VM centrale ni côté contrat API.** Cette version ne touche que le frontend du poste : mêmes routes, mêmes réponses, même session (identifiant/jeton via le gestionnaire d'identifiants Windows).

**Livraison du build sans étape supplémentaire sur le poste.** Il n'existe aujourd'hui aucune CI (`.github/workflows/` absent) et l'installation d'un poste est « `git clone` + `pip install -e` », sans étape de build ; les fichiers `static/` sont committés tels quels. Le dossier compilé par Vite (`dist/`) est donc committé directement dans `poste/src/poste/static/`, exactement comme les fichiers actuels — Node.js ne tourne jamais en production sur le poste, seulement au moment où la personne (ou l'agent IA de dev) qui fait évoluer le code lance `npm run build` avant de committer. Une CI/CD qui prendrait en charge ce build est notée pour plus tard dans la feuille de route, pas construite ici.

**Pas de tests frontend dédiés cette version.** Convention `CLAUDE.md` : tests HTTP-boundary, jamais de test d'appel de fonction interne — ce qui exclut des tests unitaires de composants React. Le backend est inchangé (déjà couvert par la suite pytest existante) ; la validation de l'écran redessiné se fait visuellement par un compte administrateur. Un filet de sécurité automatisé côté UI (Playwright) est noté pour une version future dans la feuille de route.

## User Stories

1. En tant que compte administrateur, je veux que l'écran comptes n'affiche plus en permanence tous les formulaires (modification, création, confirmations), afin de retrouver rapidement le tableau des comptes sans devoir faire défiler du contenu qui ne me concerne pas à l'instant.
2. En tant que compte administrateur, je veux créer, modifier, changer le statut administrateur ou supprimer un compte depuis une fenêtre modale dédiée à cette seule action, afin que l'action en cours soit visuellement isolée du reste de l'écran.
3. En tant que compte administrateur, je veux continuer à saisir la Clé d'administration VM dans la modale de suppression et de changement de statut administrateur, afin que rien ne change côté sécurité par rapport à aujourd'hui.
4. En tant que collaborateur, je veux que le chat, la consommation et le profil de travail se comportent exactement comme avant (mêmes échanges avec la VM centrale), afin que cette version n'apporte que du confort visuel, pas un changement de comportement.
5. En tant que collaborateur ou compte administrateur, je veux que l'installation ou la mise à jour de mon poste reste un simple `git pull` + double-clic sur le lanceur, afin de ne jamais avoir besoin d'installer Node.js ou de lancer un build moi-même.
6. En tant que futur mainteneur (agent IA de développement), je veux une base React/TypeScript/Vite avec des composants réutilisables (shadcn/ui), afin de pouvoir ajouter les nombreux écrans des versions 1.3.0/1.4.0 et suivantes sans repartir d'un unique fichier JavaScript toujours plus long.
7. En tant que futur mainteneur, je veux que le typage TypeScript attrape des erreurs à la compilation, afin de compenser l'absence de relecture humaine technique sur le code que je produis.
8. En tant que responsable du projet, je veux que le style reste simple pour cette version (pas de recherche esthétique poussée), afin de livrer vite un gain d'UX mesurable avant d'investir plus tard dans le style.

## Implementation Decisions

- **Nouveau dossier `poste/frontend/`** : source React/TypeScript/Vite/Tailwind/shadcn-ui, avec son propre `package.json` (jamais installé ni buildé sur le poste en production). `vite.config.ts` configure `build.outDir` pour écrire directement dans `poste/src/poste/static/`, afin que `main.py` (`_STATIC_DIR`, `StaticFiles`, `FileResponse`) n'ait rien à changer.
- **Écrans réécrits en composants React**, un par section actuelle : `EcranConnexion`, `EcranChangementMotDePasse`, `EcranCompte` (coquille : en-tête + navigation par onglets), puis par onglet : `OngletChat`, `OngletConsommation`, `OngletProfilTravail`, `OngletComptes` (admin), `OngletConsommations` (admin) — même découpage fonctionnel qu'`index.html` aujourd'hui.
- **`OngletComptes`** : le tableau des comptes reste affiché par défaut ; un bouton « Créer un compte » ouvre une `Dialog` shadcn/ui portant le formulaire de création (avec révélation du mot de passe généré à la fermeture réussie) ; chaque ligne du tableau ouvre, selon l'action, une `Dialog` de modification, une `Dialog` de confirmation de changement de statut administrateur (champ Clé d'administration VM), ou une `Dialog` de confirmation de suppression (champ Clé d'administration VM) ; la révélation de mot de passe réinitialisé et la confirmation de déconnexion forcée s'affichent dans un composant de notification ponctuelle (toast shadcn/ui) plutôt qu'un bloc qui reste affiché.
- **Session** : la logique actuelle (lecture/écriture de l'identifiant et du jeton via les endpoints backend qui parlent au gestionnaire d'identifiants Windows) est portée dans un hook React (`useSession` ou équivalent), sans changement de contrat avec le backend `poste`.
- **TanStack Query** : un hook de requête/mutation par ressource de la VM centrale déjà appelée par `app.js` (comptes, conversations, messages, pièces jointes, consommation, profil de travail) ; invalidation du cache correspondant après chaque mutation (ex. création de compte invalide la liste des comptes).
- **Navigation** : état React local (pas de `react-router`) pour basculer entre les trois écrans racine et entre les onglets d'`EcranCompte` — même logique qu'aujourd'hui, sans URL.
- **`poste/pyproject.toml`** : aucun changement de packaging attendu — `static/` reste inclus dans le wheel comme aujourd'hui (packaging par défaut de hatchling sur `src/poste`), que son contenu soit écrit à la main ou produit par `vite build`.
- **[ADR-0010](../adr/0010-front-poste-react-typescript-vite.md)** documente ce choix de stack front (React/TypeScript/Vite/shadcn-ui/Tailwind, build committé dans git, jamais de Node.js en production sur le poste) — [ADR-0001](../adr/0001-backend-local-par-poste.md) (backend local par poste) reste valable, cette décision la complète sans la contredire.

## Testing Decisions

Aucun test frontend dédié pour cette version (décidé pendant le grilling — voir Solution). Le contrat HTTP entre le poste et la VM centrale ne change pas : la suite pytest existante (frontière HTTP, réponses observables, `CLAUDE.md`) continue de couvrir la VM centrale sans modification. La validation de l'écran comptes redessiné (et des autres écrans migrés) se fait visuellement par un compte administrateur avant de considérer la version terminée. Un filet de sécurité automatisé côté UI (Playwright) est noté dans la feuille de route pour une version future, pas construit ici.

## Out of Scope

- Tests automatisés frontend (Playwright ou autre) — reporté, noté dans la feuille de route.
- CI/CD pour builder le front automatiquement — reporté ; le dossier `dist/` compilé est committé directement pour l'instant.
- Routage par URL / deep-linking entre écrans.
- Tout changement côté VM centrale ou du contrat API — cette version ne touche que le frontend du poste.
- Recherche esthétique poussée au-delà de ce que produisent le plugin `frontend-design` et shadcn/ui par défaut — « simple au début », comme indiqué dans la feuille de route.
- Le futur agent IA de continuation du développement et son flux de validation par compte administrateur — noté dans la feuille de route pour une version future, pas construit ici.
- Lanceur poste (exécutable pywebview) — sujet distinct de la feuille de route, inchangé.
