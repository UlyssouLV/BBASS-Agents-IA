# V1.3.0 — Inspecteur des échanges avec le modèle (outil de développement)

## Problem Statement

Côté UI, on ne voit aujourd'hui que ce qui est affiché dans le chat : le message du collaborateur et la réponse de l'IA. Tout le reste de ce qui part réellement vers Mistral est invisible :

- Le prompt réel du tour de chat principal (style 1.2.2, résumé glissant, profil de travail, message système pièce jointe, fenêtre des 3 derniers messages) n'est jamais affiché nulle part — seul le texte final de la réponse l'est.
- Les appels annexes (titrage de la conversation, résumé+profil en arrière-plan, OCR/vision sur une pièce jointe, tool calling pour relire une pièce jointe hors fenêtre) sont complètement invisibles : ils ne laissent de trace aujourd'hui que des métadonnées agrégées dans la table `Consommation` (type d'appel, tokens, coût) — jamais le contenu envoyé ni la réponse brute.
- Rien ne permet de distinguer un appel qui a réussi d'un appel qui a échoué (erreur réseau, timeout, réponse malformée) : `routers/conversations.py` fait un `db.rollback()` et renvoie une 502 générique, sans garder de trace de ce qui avait été envoyé au moment de l'échec.
- Il n'existe aucun moyen de retrouver, après coup, pourquoi une réponse donnée est sortie comme elle est sortie (mauvais style, oubli du profil de travail, confusion sur une pièce jointe) sans reconstruire mentalement le prompt à partir du code.

Ceci bloque le débogage du style de réponse (1.2.2), et deviendra plus aigu avec les futurs Agents métier (1.4.0 Moduléo, 1.5.0 n8n) et le traitement par pôle des pièces jointes (1.6.0), où le prompt réel sera encore plus composite.

## Solution

Un **mode développeur**, accessible depuis n'importe quel compte (pas réservé aux comptes administrateur), qui ouvre dans un nouvel onglet une vue technique listant, pour une conversation choisie, **tous les appels Mistral réels dans l'ordre chronologique** (chat principal, titrage, résumé+profil, OCR, vision, et chaque aller-retour de tool calling), chacun avec le payload exact envoyé et la réponse brute reçue — pas seulement les bulles user/assistant visibles dans le chat normal.

**Déclenchement.** Un raccourci clavier discret (`Ctrl+Maj+D`), actif en arrière-plan sur tout écran du poste, ouvre un nouvel onglet vers une route dédiée (`/inspecteur`). Cette route demande la **clé d'administration VM** (`VM_ADMIN_KEY`, déjà utilisée aujourd'hui en en-tête `X-Admin-Key` pour les actions sensibles du panel Comptes — promotion, rétrogradation, suppression) avant de charger quoi que ce soit : même champ, même libellé (« Clé d'administration VM ») et même comportement que le composant existant (`OngletComptes.tsx`, ex. ligne 488) — saisie en mémoire pour cet onglet, jamais stockée en `localStorage`, à ressaisir à chaque nouvelle ouverture. Aucun nouveau secret, aucun nouveau flag sur `Compte` (pas de `est_admin` requis sur le compte connecté).

**Portée volontairement assumée.** Une fois débloqué, le mode développeur donne accès à **toutes les conversations, tous comptes confondus** — rupture explicite avec la règle actuelle de l'onglet Consommations admin (`OngletConsommations.tsx`) qui ne montre jamais le détail d'une conversation individuelle. C'est un outil de débogage technique (même esprit qu'une console F12), pas un écran métier ; le verrou `VM_ADMIN_KEY` est jugé suffisant pour cette portée (à documenter dans un ADR, cf. Further Notes).

**Navigation.** Liste des comptes ayant au moins une conversation → liste des conversations de ce compte → fil chronologique de la conversation, où chaque entrée est un **échange technique** (un appel Mistral, succès ou échec) plutôt qu'un message visible, cliquable pour déplier le payload complet envoyé et la réponse brute reçue. Historique seulement, rafraîchi manuellement (pas de suivi en direct dans cette version).

**Capture.** Chaque appel réel vers Mistral (`MistralClient.chat()` et `.ocr()`, `vm-centrale/src/vm_centrale/mistral_client.py`) est capturé : le payload exact tel que construit juste avant l'appel HTTP (donc après assemblage par `_construire_messages_pour_mistral`, `_prompt_titrage`, `_prompt_resume_et_profil`, `_outils_piece_jointe`, ou le payload vision de `analyse_pieces_jointes/image.py`), et la réponse brute telle que reçue — y compris quand Mistral répond par une demande d'appel d'outil (`AppelOutilDemande`) plutôt qu'un contenu final : chaque aller-retour de tool calling est donc deux échanges distincts dans l'inspecteur (la demande d'outil, puis le second appel une fois le résultat de l'outil réinjecté), ce qui montre naturellement ce que l'outil a renvoyé sans mécanisme de capture séparé pour l'exécution de l'outil elle-même. Un appel qui échoue (erreur réseau, statut HTTP en erreur, réponse malformée) est capturé aussi, avec son statut d'échec — et doit survivre au `db.rollback()` que fait l'appelant dans ce cas (cf. Implementation Decisions), sinon l'échange qu'on veut le plus déboguer disparaîtrait.

**Pièces jointes dans le payload.** Le payload capturé est fidèle à ce qui a réellement été envoyé, y compris le texte intégral d'un extrait de pièce jointe injecté dans un message système (`contenu_extrait`, potentiellement volumineux). Pour ne pas répéter ce texte une deuxième fois dans l'inspecteur et éviter un mur de texte à l'affichage, l'échange garde une référence (`piece_jointe_id`) vers la pièce jointe concernée quand il y en a une ; l'interface affiche cette partie du payload comme une **référence cliquable** (« Pièce jointe : nom_fichier — voir ») plutôt qu'en clair, et renvoie vers le contenu déjà consultable de cette pièce jointe plutôt que de le dupliquer.

**Sécurité.** La clé API Mistral (`MISTRAL_API_KEY`) n'est de toute façon jamais dans le payload applicatif capturé : elle est ajoutée en en-tête HTTP (`Authorization: Bearer ...`) séparément du corps JSON construit, après le moment où ce corps serait capturé — rien à neutraliser spécifiquement pour ça, mais à couvrir par un test qui vérifie qu'aucun échange stocké ne contient jamais la clé ni l'en-tête `Authorization`.

## User Stories

1. En tant que développeur, je veux ouvrir un mode développeur depuis n'importe quel compte avec un raccourci clavier, afin de ne pas devoir me reconnecter avec un compte spécifique pour déboguer.
2. En tant que développeur, je dois saisir la clé d'administration VM pour ouvrir ce mode, afin que l'accès à tout le contenu des conversations reste verrouillé par un secret déjà en place.
3. En tant que développeur, je veux que ce mode s'ouvre dans un nouvel onglet, afin de garder mon poste de travail (chat en cours) inchangé pendant que je débogue.
4. En tant que développeur, je veux choisir un compte puis une de ses conversations, afin de retrouver l'échange précis que je veux inspecter.
5. En tant que développeur, je veux voir, pour une conversation, tous les appels Mistral dans l'ordre chronologique (chat, titrage, résumé+profil, OCR, vision, tool calling), afin de comprendre exactement ce qui s'est passé au-delà des bulles affichées dans le chat.
6. En tant que développeur, je veux déplier un échange et voir le payload exact envoyé (messages système/user/assistant, outils proposés, modèle) ainsi que la réponse brute reçue, afin de déboguer un problème de style, de contenu ou de contexte.
7. En tant que développeur, je veux voir qu'un appel a échoué (et pourquoi, dans la mesure du disponible) plutôt que de ne rien voir du tout, afin de déboguer une erreur de relais sans devoir la reproduire en conditions réelles.
8. En tant que développeur, je veux qu'un appel de tool calling apparaisse comme deux échanges liés (la demande d'outil, puis le second appel une fois le résultat réinjecté), afin de voir ce que l'outil a réellement renvoyé à Mistral.
9. En tant que développeur, je veux qu'une pièce jointe mentionnée dans un payload soit une référence cliquable plutôt qu'un bloc de texte brut dupliqué, afin de garder l'affichage lisible même pour un gros document.
10. En tant que développeur, je veux que l'inspecteur couvre toutes les conversations de tous les comptes, afin de pouvoir déboguer le poste d'un collègue sans qu'il ait besoin d'être présent.
11. En tant que collaborateur dont une conversation est inspectée, je veux que ce contenu ne soit visible que par quelqu'un qui connaît la clé d'administration VM, afin que ma conversation ne soit pas consultable par n'importe qui sur le LAN.
12. En tant que collaborateur, je veux que la suppression d'une de mes conversations efface aussi les échanges techniques associés, afin que mon contenu ne traîne pas indéfiniment ailleurs après coup.
13. En tant que compte administrateur, je veux que les lignes `Consommation` existantes (facturation) ne soient pas modifiées par cette version, afin que le suivi de coût déjà en place reste fiable et inchangé.
14. En tant que développeur, je veux que l'instrumentation de temps posée en 1.2.3 reste disponible pour cette vue si pertinent, sans devoir reconstruire un système de mesure séparé.
15. En tant que compte administrateur qui valide cette version, je veux que la suite de tests pytest existante (auth, conversations, pièces jointes, comptes, consommation) reste verte, afin de vérifier qu'aucune fonctionnalité actuelle n'a régressé.

## Implementation Decisions

- **Déclenchement front** : un écouteur clavier global (`Ctrl+Maj+D`) monté au niveau racine de l'application `poste/frontend`, actif quel que soit l'écran affiché, ouvre un nouvel onglet vers une route dédiée `/inspecteur` (`window.open`). Cette route est un point d'entrée séparé de l'application principale (pas un onglet de plus dans `PagePanelAdministration.tsx`), avec son propre écran de saisie de la clé avant tout chargement de données.
- **Authentification de la route `/inspecteur`** : chaque requête vers les nouveaux endpoints porte à la fois le jeton du compte connecté (`get_identifiant_compte_du_jeton`, n'importe quel compte) et l'en-tête `X-Admin-Key` (`exiger_cle_admin_vm`, déjà défini dans `vm-centrale/src/vm_centrale/autorisation.py`) — même combinaison de dépendances que les endpoints sensibles de `routers/comptes.py`, sans introduire de nouvelle notion d'autorisation.
- **Nouveaux endpoints (vm-centrale, proxyfiés par `poste` comme le reste de l'API)** : `GET /inspecteur/comptes` (comptes ayant au moins une conversation), `GET /inspecteur/comptes/{identifiant_compte}/conversations`, `GET /inspecteur/conversations/{conversation_id}/echanges` (liste chronologique), `GET /inspecteur/echanges/{id}` (détail : payload complet, réponse brute, référence pièce jointe, statut/erreur).
- **Nouvelle table `echanges_inspecteur`** (`vm-centrale/src/vm_centrale/models.py`), séparée de `Consommation` : `id`, `identifiant_compte`, `conversation_id` (FK `conversations.id`, **`ON DELETE CASCADE`** — contrairement à `Consommation` qui survit à la suppression de la conversation), `piece_jointe_id` (FK `pieces_jointes.id`, nullable), `type_appel` (même vocabulaire que `Consommation` : `chat`/`titrage`/`resume_et_profil`/`ocr`/`vision`), `modele`, `requete_payload` (JSON, payload exact envoyé), `reponse_payload` (JSON, nullable), `statut` (`succes`/`echec`), `erreur` (texte, nullable), `date_creation`. Pas de colonne dérivée de `Consommation` dupliquée au-delà de ces clés nécessaires à la navigation (comptes → conversations → échanges) ; le reste (tokens, coût) continue de vivre uniquement dans `Consommation`, consultable séparément si besoin.
- **Capture dans `MistralClient`** : `mistral_client.py` reste sans dépendance DB. `ReponseChat`/`ReponseOcr` gagnent un champ `payload_envoye` (le dict juste avant le POST) et `reponse_brute` (le corps JSON reçu) ; `AppelOutilDemande` gagne les mêmes deux attributs. Chaque site d'appel existant (`routers/conversations.py`, `analyse_pieces_jointes/image.py`, `analyse_pieces_jointes/pdf.py`) écrit une ligne `echanges_inspecteur` juste à côté de son appel existant à `enregistrer_consommation`, avec les mêmes informations de contexte (`identifiant_compte`, `conversation_id`, `type_appel`) déjà disponibles à cet endroit.
- **Échanges réussis** : ajoutés à la session `db` sans commit immédiat, comme `Consommation` — un rollback plus loin dans le même tour annule aussi cette ligne, cohérent avec « aucune conversation fantôme » déjà en place.
- **Échanges en échec** : capturés et **commités indépendamment**, dans le bloc `except` au moment du `db.rollback()` existant (ex. `routers/conversations.py` ligne ~517) — sur une transaction séparée, pour que la ligne survive au rollback qui annule le reste du tour. Sans ce traitement à part, l'échange qu'on veut le plus pouvoir déboguer disparaîtrait avec le rollback.
- **Référence pièce jointe** : au site d'appel, quand une pièce jointe est injectée dans le tour courant (`piece_jointe` déjà résolu avant l'appel, ex. ligne 495-497) ou qu'un appel OCR/vision porte sur une pièce jointe précise, son `id` est passé à la capture et stocké dans `piece_jointe_id`. Le payload stocké en base reste fidèle (texte intégral inclus, comme `contenu_extrait` aujourd'hui) ; c'est l'affichage front qui, en présence de `piece_jointe_id`, remplace ce bloc par une référence cliquable au lieu de l'extrait brut.
- **Front `/inspecteur`** : trois écrans en profondeur (comptes → conversations → fil chronologique), même pattern `Table` shadcn/ui que `OngletComptes.tsx`/`OngletConsommations.tsx` pour les deux premiers niveaux ; le fil chronologique réutilise le rendu de fil de `OngletChat` en remplaçant les bulles par des cartes d'échange (type d'appel, statut, horodatage), dépliables pour voir le payload/la réponse en détail (nouveau composant, pas de pattern expandable existant à réutiliser).
- **Instrumentation de temps (1.2.3)** : `lib/instrumentationTemps.ts`/`usePerfChargementPage` peuvent être posés sur l'ouverture de `/inspecteur` et le chargement d'un fil, comme sur les autres écrans — réutilisation directe, aucune extension du système de mesure nécessaire pour cette version.

## Testing Decisions

Nouveaux seams HTTP-boundary, dans le même esprit que l'existant (`TestClient`, vraie base de test) :

- **`vm-centrale/tests/test_inspecteur.py` (nouveau)** : accès refusé sans jeton valide ; accès refusé avec jeton valide mais sans `X-Admin-Key` ou avec une mauvaise clé ; accès autorisé avec jeton (n'importe quel compte, pas seulement un compte `est_admin`) + bonne clé. Listing comptes → conversations → échanges dans l'ordre chronologique. Détail d'un échange réussi (payload, réponse) et d'un échange en échec (statut, pas de réponse). Un échange en échec doit être retrouvable même quand le tour applicatif qui l'a produit a fait un rollback (test qui force un échec de `client.chat()` et vérifie que la ligne `echanges_inspecteur` existe malgré tout). Un échange capturé ne contient jamais la clé API Mistral ni l'en-tête `Authorization`. Suppression d'une conversation : ses `echanges_inspecteur` disparaissent avec elle (cascade), contrairement à ses lignes `Consommation` qui doivent toujours survivre (non-régression explicite sur 1.1.3).
- **`vm-centrale/tests/test_conversations.py` / `test_pieces_jointes.py` (existants, étendus)** : chaque site d'appel Mistral (chat principal, titrage, résumé+profil, tool calling, OCR, vision) produit bien une ligne `echanges_inspecteur` en plus de sa ligne `Consommation` déjà testée, avec le bon `type_appel` et, quand applicable, le bon `piece_jointe_id`.
- **`poste/tests/` (existant, étendu)** : les nouveaux endpoints `/inspecteur/*` sont bien proxyfiés vers `vm-centrale` avec le jeton **et** l'en-tête `X-Admin-Key` transmis tels quels.
- **Front (`poste/frontend`)** : aucun outillage de test UI automatisé introduit (cohérent avec l'état assumé depuis 1.2.0) — validation visuelle manuelle du raccourci clavier, de l'écran de saisie de clé, de la navigation à trois niveaux, et du rendu « référence pièce jointe » au lieu du texte brut.
- Le reste de la suite pytest existante (auth, comptes, consommation, concurrence) doit rester vert sans modification : aucun changement de contrat API existant, uniquement des ajouts.

## Out of Scope

- Suivi en direct d'une conversation en cours (auto-refresh/websocket) : historique seulement, rafraîchi manuellement pour cette version.
- Rétro-capture des échanges déjà passés avant cette version : seuls les appels faits après la mise en production sont dans `echanges_inspecteur`, rien n'est reconstruit pour l'historique déjà en base.
- Nouveau flag « dev » sur `Compte` : la portée « n'importe quel compte » s'appuie uniquement sur `VM_ADMIN_KEY`, pas sur un nouveau champ du modèle `Compte`.
- Export/téléchargement d'un échange (JSON à partager) : pas construit dans cette version, pourra être ajouté plus tard si le besoin se confirme.
- Politique de purge/rétention indépendante de la suppression de conversation (ex. purger après 30 jours même si la conversation existe encore) : la seule règle de cycle de vie pour cette version est « disparaît avec la conversation ».
- Modification de la table `Consommation` ou de son contrat de lecture (`OngletConsommations.tsx`, confidentialité par compte sans détail de conversation) : inchangés, l'inspecteur est un système de données séparé.
- Capacité d'écriture depuis l'inspecteur (rejouer un appel, modifier un payload et le renvoyer à Mistral) : lecture seule dans cette version.

- **Glossaire (`CONTEXT.md`)** : « mode développeur » / « inspecteur des échanges avec le modèle » sont de nouveaux termes produits (pas de simples détails d'implémentation) — à ajouter.
