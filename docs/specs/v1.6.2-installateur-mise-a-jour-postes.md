# V1.6.2 — Installateur et mise à jour automatique des postes

Parent GitHub : [#238](https://github.com/UlyssouLV/BBASS-Agents-IA/issues/238).

## Problem Statement

- **Le poste ne s’installe que depuis un clone du dépôt.** `lancer-logiciel.bat` exige git, Python 3.11, des venv, Docker, démarre en plus une VM locale avec Postgres et SearXNG, sème un compte de test et ouvre des fenêtres de terminal puis un onglet de navigateur. Ce n’est pas une installation pour un collaborateur.
- **Rien ne relie la version d’un poste à celle de la VM.** Depuis la 1.6.1, la VM prod change de version par « Promouvoir en prod » ; chaque poste, lui, reste sur ce qu’on a copié à la main. Un poste plus ancien ou plus récent que la VM appelle des routes qui n’existent pas ou plus.
- **Pas de vraie application.** Le chat vit dans un onglet de navigateur ; fermer la console arrête tout ; aucune icône, aucun démarrage avec Windows, aucun écran qui dise ce qui se passe au lancement.
- **L’adresse de la VM n’est réglable qu’en éditant un `.env`** dans le clone.

## Solution

Livrer le **poste comme une application Windows** qui s’installe sans git ni droits administrateur, et qui **se met à jour d’elle-même à chaque lancement sur la version de la VM** à laquelle elle est reliée.

1. **Forme du paquet.** Application Windows 10/11 **x64** native, sans Docker. Un **Lanceur** en **Rust / Tauri v2** (fenêtre, zone de notification, mise à jour, installateur) démarre le **backend poste Python actuel, inchangé**, figé par PyInstaller en mode dossier (`onedir`) et lancé comme *sidecar*. Le front React existant (ADR-0010) est affiché dans la fenêtre.
2. **Version dictée par la VM.** À chaque lancement, le Lanceur lit `GET /sante` sur le Serveur BBASS configuré et obtient sa version. Si elle diffère de la version installée, il télécharge depuis la **GitHub Release** `vX.Y.Z` le **Paquet poste** `bbass-poste-vX.Y.Z-windows-x64.zip`, vérifie sa **signature ed25519** (clé privée dans un secret GitHub, clé publique dans le Lanceur), le décompresse dans `versions\vX.Y.Z\`, bascule, et garde **une** version précédente. La VM ne livre que le numéro ; les octets viennent d’Internet. Conséquence voulue : un poste se met à jour quand la VM prod passe à cette version (Release puis « Promouvoir en prod », 1.6.1) ; poste et VM restent de la même version.
3. **Retour arrière.** Si la nouvelle version ne répond pas en local après la bascule, le Lanceur remet l’ancien Lanceur et l’ancienne version et le journalise.
4. **Mise à jour du Lanceur lui-même.** Chaque Paquet poste contient le Lanceur **et** le backend. À la bascule, le Lanceur renomme son propre exe en `BBASS.old.exe` (permis par Windows pendant l’exécution), pose le nouveau, redémarre ; en cas d’échec, il remet l’ancien. Séquence documentée dans l’ADR-0022.
5. **Hors ligne ou décalé.** VM ou Internet injoignable, téléchargement ou signature en échec : le logiciel démarre sur la version installée, avec un bandeau : « Mise à jour vers vX.Y.Z impossible : certaines fonctionnalités peuvent ne pas fonctionner tant qu’elle n’a pas réussi. Nouvel essai au prochain lancement. » (sans numéro si la VM est injoignable). Pas de mise à jour pendant que le logiciel tourne en fond, sauf demande explicite (point 9).
6. **Écran de démarrage** soigné, à l’identité visuelle 1.2.1 : « Vérification… », « Mise à jour vers vX.Y.Z… » avec barre de progression, « Démarrage… ». Erreurs en français clair, sans pile technique.
7. **Fenêtre et fond.** Fenêtre native **WebView2** (moteur Edge déjà présent dans Windows, partagé, rien à livrer) avec icône et titre BBASS. Fermer la fenêtre laisse le logiciel dans la **zone de notification** : « Ouvrir BBASS », « Ouvrir dans le navigateur » (`http://127.0.0.1:8100`), « Quitter ». **Instance unique** : relancer BBASS rouvre la fenêtre. **Démarrage avec Windows** (option, cochée par défaut) : lancement en fond sans fenêtre, mise à jour faite à ce moment.
8. **Installateur maison, beau et efficace.** `BBASS-Setup-vX.Y.Z.exe` est le Lanceur lui-même : lancé alors que rien n’est installé, il ouvre un assistant React dans une fenêtre WebView2, au style de l’application :
   1. **Bienvenue** : logo, version, emplacement d’installation ;
   2. **Serveur BBASS** : hôte et port (8000), pré-remplis par la constante d’adresse prod si elle est connue, pastille de test en direct sur `/sante` (vert avec la version, orange sinon) ; continuer en orange est permis ;
   3. **Options** : démarrer avec Windows, raccourci sur le Bureau (cochées) ;
   4. **Installation** : progression, puis **Lancer BBASS**.
   Installation **par utilisateur, sans droits administrateur**, dans `%LOCALAPPDATA%\BBASS` ; raccourcis Menu Démarrer (et Bureau) ; entrée de désinstallation dans `HKCU`. Le Setup **embarque sa version** (installation hors ligne possible) ; le premier lancement s’aligne ensuite sur la VM.
9. **Écran de connexion revu et menu « … ».** Écran de connexion en deux panneaux (marque à gauche, formulaire à droite), dans notre propre style 1.2.1 ; **pastille d’état** du Serveur BBASS (`/sante` : vert « Connecté à BBASS vX.Y.Z », orange « Serveur BBASS injoignable, nouvel essai… »). Un bouton **« … »** ouvre :
   - **Configuration** : Serveur BBASS (hôte, port), **Tester la connexion**, Annuler / Enregistrer ;
   - **Ouvrir le dossier de configuration** (configuration et journaux) ;
   - **À propos** : version du poste, version de la VM, date et résultat de la dernière vérification de mise à jour, bouton **Vérifier les mises à jour maintenant** (même parcours qu’au lancement, puis redémarrage).
   Accessible sans connexion (on en a besoin quand on ne peut pas se connecter) et, une fois connecté, depuis le menu du profil.
10. **Un seul Environnement côté poste : prod.** Aucun choix d’Environnement dans l’installateur. Pour essayer le staging, on change l’hôte ou le port (Configuration ou fichier de configuration) ; la mise à jour suit alors automatiquement la version du staging. L’adresse prod par défaut est une constante du dépôt ; **vide tant qu’elle n’est pas connue** : alors le premier lancement ouvre directement la Configuration.
11. **Configuration et journaux.** Fichier de configuration dans `%LOCALAPPDATA%\BBASS\` (adresse du Serveur BBASS, démarrage avec Windows), lu par le Lanceur et par le backend. La Session reste dans le gestionnaire d’identifiants Windows (keyring, par utilisateur, sans droits administrateur). Journaux du Lanceur et du backend dans `%LOCALAPPDATA%\BBASS\journaux\` (rotation, quelques Mo au plus), **sans secret ni jeton**.
12. **Désinstallation** par « Applications installées » : supprime programme, versions, démarrage automatique et la Session du gestionnaire d’identifiants ; **garde la configuration**. Les conversations vivent sur la VM.
13. **CI et Release.**
    - Nouveau compartiment **`build-poste-windows`** (runner Windows, path filter + skip→vert, ADR-0020) : build du front, du sidecar PyInstaller et du Lanceur, puis test de fumée (le paquet démarre et répond en local). Ajouté aux checks requis du ruleset `main` (geste humain, guide dans l’ADR-0022).
    - Nouveau compartiment **`tests-lanceur`** : `cargo test` (et `clippy`).
    - À chaque GitHub Release : un workflow joint à la Release `bbass-poste-vX.Y.Z-windows-x64.zip`, sa signature, `BBASS-Setup-vX.Y.Z.exe` et `SHA256SUMS`. Dépôt public : aucun jeton côté poste.
14. **Pas de certificat Authenticode.** SmartScreen avertit une seule fois, à l’installation ; la doc montre comment passer. Les mises à jour passent par notre propre vérification de signature.
15. **Dev inchangé.** `lancer-logiciel.*` et `lancer-vm.*` restent dans le dépôt pour le développement et ne sont **jamais** dans le paquet installé. Le backend lit toujours son `.env` en dev.
16. **Docs.**
    - **ADR-0022** « Poste livré en application Windows native, version dictée par la VM » : Docker sur poste écarté (keyring, Docker Desktop sur chaque poste), Electron écarté (Chromium embarqué), .NET écarté (macOS faible), Rust/Tauri retenu (légèreté de WebView2 partagé, portabilité macOS future), updater maison plutôt que `tauri-plugin-updater` (version dictée par la VM, versions côte à côte, retour arrière), séquence de bascule du Lanceur, pas de certificat.
    - **Glossaire** : **Lanceur**, **Paquet poste**, **Serveur BBASS** (adresse configurée de la VM côté poste).
    - **Site de doc** : guide collaborateur (installer, passer SmartScreen, fenêtre et zone de notification, menu « … », mise à jour échouée) et guide admin (promouvoir en prod = mettre à jour tous les postes, changer l’adresse, basculer un poste sur le staging). Courts : la 1.7 refond le site.
    - **Outillage agent** : test-root `lanceur` dans `agents/roles.yml`, `lancer-tests` sait lancer `cargo test`, `AGENTS.md` mentionne Rust pour le Lanceur.
    - **Feuille de route** (`/afr` sur la branche) : 1.6.2 renommée et « conteneurs » retiré ; Plus tard : **Optimisation du système** (backend poste dans le Lanceur en Rust : gains et coûts chiffrés, déclencheurs, alternatives étudiées), **Portage macOS** (Tauri/WKWebView, Trousseau, notarisation Apple), **Certificat de signature Windows** (déclencheur : déploiement au-delà du pilote), **Paquets ARM64**.

## User Stories

1. En tant que collaborateur, je veux installer BBASS en lançant un seul fichier, sans droits administrateur ni git, afin d’être autonome.
2. En tant que collaborateur, je veux un assistant d’installation clair et soigné qui me demande l’adresse du serveur et la teste, afin de savoir tout de suite si mon poste est bien relié.
3. En tant que collaborateur, je veux que BBASS se mette à jour tout seul au lancement, afin de ne jamais avoir à télécharger une nouvelle version.
4. En tant que collaborateur, je veux voir ce que fait BBASS au lancement (vérification, mise à jour, démarrage), afin de ne pas croire qu’il est planté.
5. En tant que collaborateur, je veux que BBASS démarre même sans Internet ou sans serveur, et qu’il me dise que la mise à jour a échoué et que certaines fonctionnalités peuvent ne pas marcher, afin de comprendre ce qui se passe.
6. En tant que collaborateur, je veux une vraie fenêtre BBASS avec son icône, qui reste disponible dans la zone de notification quand je la ferme, afin de la retrouver instantanément.
7. En tant que collaborateur, je veux pouvoir ouvrir BBASS dans mon navigateur depuis l’icône, afin de travailler comme je préfère.
8. En tant que collaborateur, je veux que BBASS démarre avec Windows (désactivable), afin qu’il soit prêt quand j’en ai besoin.
9. En tant que collaborateur, je veux un écran de connexion qui m’indique si le serveur répond, afin de savoir si le problème vient de mon mot de passe ou du serveur.
10. En tant qu’admin du cabinet, je veux changer l’adresse du serveur depuis le menu « … » de l’écran de connexion, sans connexion préalable, afin de dépanner un poste mal configuré.
11. En tant qu’admin du cabinet, je veux qu’une promotion en prod mette à jour tous les postes à leur prochain lancement, afin de n’avoir qu’un seul geste à faire.
12. En tant qu’admin du cabinet, je veux qu’une version de poste qui ne démarre pas soit remplacée automatiquement par la précédente, afin que le collaborateur garde un chat qui marche.
13. En tant qu’admin du cabinet, je veux voir dans « À propos » la version du poste, celle de la VM et le résultat de la dernière mise à jour, et lancer une vérification à la main, afin de diagnostiquer sans outil.
14. En tant qu’admin du cabinet, je veux un journal sans secret accessible depuis « Ouvrir le dossier de configuration », afin de me le faire envoyer en cas de problème.
15. En tant que développeur, je veux pointer un poste vers le staging en changeant seulement l’adresse, afin d’essayer une version avant la prod.
16. En tant que responsable sécurité, je veux que seuls des paquets signés par la CI soient installés par la mise à jour, afin qu’une Release ou un téléchargement altéré ne s’installe jamais.
17. En tant que collaborateur, je veux désinstaller BBASS depuis « Applications installées », afin de ne rien laisser de ma session derrière moi.
18. En tant que développeur, je veux que chaque PR qui touche le poste ou le Lanceur prouve que le paquet se construit et démarre, afin qu’un paquet cassé n’arrive jamais sur `main`.
19. En tant que développeur, je veux que `lancer-logiciel.*` reste inchangé, afin que la 1.6.2 ne casse pas mon poste de travail.

## Implementation Decisions

- **Dépôt :** nouveau dossier `lanceur/` (crate Rust Tauri v2 + petit front React/Vite pour l’installateur et l’écran de démarrage, reprenant les jetons de style de `poste/frontend`). `poste/` reste le backend Python et le front de l’application.
- **Plugins Tauri utilisés :** zone de notification, instance unique, démarrage automatique, shell/sidecar. **Pas** `tauri-plugin-updater` ni le bundler NSIS/MSI : mise à jour et installation sont notre code.
- **Logique de mise à jour en module Rust pur** (décision de version d’après `/sante`, vérification de signature, bascule, retour arrière, cas hors ligne), sans I/O réseau dans le cœur, pour être testée par `cargo test`.
- **Signature :** ed25519 ; clé privée en secret GitHub `POSTE_CLE_SIGNATURE`, clé publique compilée dans le Lanceur.
- **Sidecar :** PyInstaller `onedir` ; port local 8100 inchangé ; le backend lit l’adresse du Serveur BBASS dans le fichier de configuration de `%LOCALAPPDATA%\BBASS` en mode paquet, `.env` en dev.
- **Backend poste :** nouvelles routes locales pour la Configuration (lire, tester, enregistrer l’adresse), l’état du Serveur BBASS et « À propos » ; « Vérifier les mises à jour maintenant » demande au Lanceur de redémarrer en mode vérification.
- **Désinstallation :** sous-commande du Lanceur inscrite dans `HKCU\…\Uninstall`.
- **Adresse prod par défaut :** constante du dépôt, vide en 1.6.2 tant qu’elle n’est pas connue.
- **Pas de certificat Authenticode** en 1.6.2.

## Testing Decisions

- **`cargo test` (test-root `lanceur`)** : version identique → pas de téléchargement ; version différente → téléchargement, signature vérifiée, bascule ; signature invalide → refus et version installée ; VM injoignable → version installée + bandeau ; nouvelle version muette → retour à l’ancienne (Lanceur et backend) ; une seule version précédente gardée ; adresse vide → Configuration au premier lancement.
- **pytest HTTP-boundary (test-root `poste`)** : routes de Configuration (lecture, test via `/sante` simulé, enregistrement), état du Serveur BBASS, « À propos » ; journal sans jeton.
- **CI `build-poste-windows`** : paquet construit et démarré, réponse locale.
- **Tests humains** (vrai poste Windows, sans droits admin) : installation avec SmartScreen ; assistant (pastille verte et orange) ; premier lancement ; mise à jour après promotion en prod ; démarrage sans Internet (bandeau) ; version volontairement cassée → retour automatique ; fermeture de fenêtre → zone de notification ; ouvrir dans le navigateur ; instance unique ; démarrage avec Windows ; écran de connexion et « … » (Configuration, dossier, À propos, vérification manuelle) ; bascule staging par l’adresse ; désinstallation.

## Out of Scope

- Windows ARM64, macOS, Linux (→ Plus tard).
- Certificat de signature Authenticode (→ Plus tard).
- Backend poste réécrit en Rust dans le Lanceur (→ Plus tard, « Optimisation du système »).
- Antennes hors LAN Castries, exposition Internet de la VM (ADR-0003).
- Choix d’Environnement dans l’installateur (prod seulement ; staging par l’adresse).
- Changement du contrat HTTP de la VM, du chat ou des fonctionnalités métier.
- Packaging ou CD de la VM (→ 1.6.1, inchangé).
- Écriture Moduléo (→ 1.5.2).
