# V1.6.0 — CI : versions vérifiées et prêtes à livrer

Parent GitHub : [#216](https://github.com/UlyssouLV/BBASS-Agents-IA/issues/216).

## Problem Statement

- **La validation d'une version dépend encore du poste de l'alternant.** Les tests pytest et le scan Sonar tournent déjà sur GitHub Actions, mais dans **un seul job** séquentiel (`sonar.yml` : vm-centrale → poste → Sonar). Un échec tardif coûte cher ; on ne peut pas relancer un compartiment seul.
- **Le front et le site de doc ne sont pas prouvés en CI.** Le build Vite du poste reste manuel (dist committé, [ADR-0010](../adr/0010-front-poste-react-typescript-vite.md)) ; un oubli de rebuild n'est pas détecté. Le site Docusaurus se build surtout via `deploy-docs.yml` sur `main`, pas comme check de PR.
- **Un bot écrit encore sur `main` après « Finalise la version ».** `deploy-docs.yml` pousse les aperçus README (`github-actions[bot]`), ce qui contredit le modèle ArgOS : tout doit entrer dans le **squash** de la version, pas après.

## Solution

Mettre en place une **CI compartimentée** sur **GitHub Actions** (modèle ArgOS) :

1. **Un workflow par compartiment**, avec **path filters** et jobs **skip→vert** pour ne pas bloquer le ruleset quand un compartiment n'est pas touché.
2. Compartiments : `tests-vm-centrale`, `tests-poste`, `build-front` (build Vite + **contrôle de dérive** vs `poste/src/poste/static/`), `build-docs` (build Docusaurus sur PR, sans deploy), `sonar` (**démarre en premier**, analyse CI-only, **sans** attendre les XML de couverture).
3. `deploy-docs.yml` : **build + GitHub Pages seulement** — plus aucun `git commit` / `git push` bot.
4. Les aperçus README sont produits et commités **sur la branche de version** (skill `finaliser-la-version`), donc dans le squash.
5. **Référence d'une version** = tag + GitHub Release `vX.Y.Z` (déjà créés à Finalise) ; la CI est la **preuve** que le SHA est vert.
6. **Ruleset** GitHub : squash-merge uniquement + checks required (guide humain dans l'ADR ; pas de ticket dédié).
7. **ADR-0020** fige ces décisions. Désactiver **Automatic Analysis** SonarCloud si encore active (geste UI guidé).

Hors packaging CD VM / installateur postes (1.6.1 / 1.6.2).

## User Stories

1. En tant que développeur (ou agent), je veux que les tests vm-centrale et poste tournent dans des jobs séparés, afin de voir vite quel compartiment casse et de gagner du temps en parallèle.
2. En tant que développeur, je veux que Sonar parte dès le début du workflow CI (sans attendre pytest), afin d'avoir un signal qualité tôt.
3. En tant que développeur, je veux que le build front et le build docs soient des checks de PR, afin de ne plus dépendre d'un build manuel oublié.
4. En tant que développeur, je veux que la CI échoue si le `static/` committé ne correspond pas au résultat de `npm run build`, afin de détecter une dérive du dist.
5. En tant que développeur, je veux que seuls les compartiments touchés par la PR tournent (path filters), avec un skip vert pour le ruleset, afin de ne pas attendre inutilement.
6. En tant qu'admin du dépôt, je veux un ruleset qui impose le squash-merge et les checks CI, afin que `main` ne reçoive que des SHA vérifiés.
7. En tant que cabinet, je veux qu'après « Finalise la version » aucun bot ne pousse sur `main`, afin que la référence tag/Release soit stable.
8. En tant qu'agent qui finalise, je veux produire les aperçus README sur la branche avant le squash, afin qu'ils entrent dans le même commit de merge.
9. En tant que développeur, je veux un ADR qui documente la CI ArgOS et le pas-à-pas ruleset / Sonar CI-only, afin de reconfigurer sans réinventer.
10. En tant que compte qui valide la version, je veux que la suite pytest locale reste verte là où le code produit n'a pas changé, et que les workflows CI soient verts sur la PR.

## Implementation Decisions

- **Hébergeur :** GitHub Actions uniquement (déjà Sonar + Pages).
- **Référence :** tag + Release ; pas d'Artifactory / registry Docker en 1.6.0.
- **Fichiers :** un YAML par compartiment sous `.github/workflows/` ; `sonar.yml` allégé (plus de pytest dedans).
- **Sonar :** CI-based analysis ; retirer l'exigence `sonar.python.coverage.reportPaths` tant que le scan ne reçoit plus les XML ; pytest reste la preuve des tests.
- **Front :** garder dist committé (ADR-0010) + drift check en CI.
- **Docs :** `build-docs.yml` sur PR ; `deploy-docs.yml` sans job `capture-readme` qui commit.
- **Process :** MAJ `finaliser-la-version` (aperçus sur branche) ; guide ruleset dans ADR-0020 ; pas de ticket GitHub « configurer le ruleset ».
- **Parallèle 1.5.2 :** branche depuis `main`, PR distincte de #207.

## Testing Decisions

- Vérifier sur une PR de la branche 1.6.0 : jobs compartimentés verts (ou skip→vert selon paths).
- Contrôle de dérive : cas volontaire (static désaligné) → job `build-front` rouge.
- Après retrait du bot : un run `deploy-docs` sur main de test / observation ne crée plus de commit aperçus.
- Tests humains : configurer le ruleset et désactiver Automatic Analysis en suivant l'ADR ; confirmer absence de push bot.
- Pytest HTTP-boundary existants : inchangés par cette version (hors régression accidentelle) — suite verte.

## Out of Scope

- CD / déploiement VM Castries (1.6.1).
- Installateur et mise à jour des postes (1.6.2).
- Attacher des assets d'install à la GitHub Release.
- Réintroduire la couverture Python dans le scan Sonar (possible plus tard).
- Runner self-host Castries, Jenkins, GitLab CI.
- Changer le modèle « dist committé » (ADR-0010) : on ajoute seulement le drift check.
