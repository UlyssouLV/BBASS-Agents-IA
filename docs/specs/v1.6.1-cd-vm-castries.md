# V1.6.1 — CD : packaging, conteneurs et mise à jour de la VM Castries sans l’alternant

Parent GitHub : [#229](https://github.com/UlyssouLV/BBASS-Agents-IA/issues/229).

## Problem Statement

- **La VM centrale ne tourne que depuis un clone du dépôt.** `lancer-vm.bat` / `.command` construisent un venv Python sur la machine, démarrent Postgres et SearXNG par Docker, sèment un compte de test (`admin` / `ChangeMoi123!`) et ouvrent des fenêtres de terminal. Rien de cela n’est une installation de serveur : il faut Python 3.11, `uv`, le dépôt, et l’alternant pour savoir quoi lancer.
- **Rien ne relie une version vérifiée (1.6.0 : tag + Release, CI verte) à ce qui tourne à Castries.** Aucune image, aucun paquet ; mettre à jour, c’est `git pull` et relancer à la main.
- **Pas d’endroit pour essayer une version avant les collaborateurs.** Une version publiée irait directement en production.
- **La maintenance prévue n’est pas branchée.** Le script de purge du cache des pages web (1.4.3) attend une crontab ; aucune convention pour les tâches planifiées.
- **Aucun moyen propre de créer le premier compte administrateur en production**, ni de renseigner les secrets chiffrés sans `scripts/chiffrer_secret.py` depuis le dépôt.

## Solution

Livrer la **VM centrale en conteneurs** et la **mettre à jour sans le dépôt**, avec deux **Environnements** (staging et prod) et une **Promotion** de l’un à l’autre :

1. **Machine cible** : une VM **Ubuntu Server 26.04 LTS** (support standard jusqu’en 2031 ; Ubuntu Pro gratuit, recommandé, jusqu’en 2036) avec Docker Engine + plugin Compose. La VM est fournie par le cabinet.
2. **Image `vm-centrale`** (Python 3.11, dépendances verrouillées par `uv.lock`, ADR-0011) et image **`searxng`** (notre `settings.yml`), construites par la CI à chaque GitHub Release et publiées **publiques** sur GHCR : `ghcr.io/ulyssoulv/bbass-vm-centrale:vX.Y.Z`, `ghcr.io/ulyssoulv/bbass-vm-searxng:vX.Y.Z`. Aucun secret dans les images.
3. **Stack Compose de production** par Environnement : `vm-centrale`, `postgres`, `searxng`. Seul le port de la VM est publié sur le LAN (prod **8000**, staging **8001**) ; Postgres et SearXNG restent sur le réseau Docker interne. Pas de HTTPS (LAN seulement, ADR-0003). Le dev (`lancer-vm.*`, `docker-compose.yml`) ne change pas.
4. **Staging et prod sur la même VM**, totalement séparés : `/opt/bbass/<env>/` (`.env` lisible par root seul, `donnees/postgres`, `donnees/pieces_jointes`, `sauvegardes/`) et `/etc/bbass/<env>/cle-maitre` (montée en lecture seule). Une clé maître par Environnement. Staging → **serveur de test Kipaware** ; prod → serveur de production Moduléo ; même clé Mistral par défaut (une ligne du `.env` pour séparer plus tard).
5. **Promotion par étiquette** : une Release `vX.Y.Z` pousse les images et pose l’étiquette **`staging`** sur cette version. Un workflow manuel **« Promouvoir en prod »** (paramètre : version) pose l’étiquette **`prod`** sur ces **mêmes** images, sans rebuild ; il refuse une version qui n’a jamais porté l’étiquette `staging`. Revenir en arrière = promouvoir l’ancienne version. Chaque promotion est tracée dans l’historique Actions.
6. **Mise à jour = une commande ou un redémarrage.** Un service systemd par Environnement (`bbass-vm-<env>.service`) et la commande `mettre-a-jour <env>` déroulent la même séquence :
   1. télécharger les images de l’étiquette de l’Environnement ;
   2. si la version a changé : sauvegarde `pg_dump`, puis démarrage ;
   3. attendre `GET /sante` ; sans réponse saine → remettre les images précédentes et le dire (journal + sortie de commande) ;
   4. sans Internet : démarrer avec les images déjà présentes et le journaliser.
   Les fichiers de déploiement (`compose.yml`, scripts, `taches-planifiees.conf`, unités systemd) **voyagent dans l’image** et sont rafraîchis à chaque mise à jour ; le `.env` n’est jamais écrasé.
7. **Installation en une commande** (`docker run --rm … ghcr.io/ulyssoulv/bbass-vm-centrale:<tag> installer <env>`), un Environnement à la fois :
   - **génère** mot de passe Postgres, clé maître, `VM_ADMIN_KEY` ; les valeurs générées sont affichées **une seule fois** à la fin, à ranger dans le gestionnaire de mots de passe du cabinet ;
   - **demande en clair** (saisie masquée) la clé API Mistral, puis la clé API et le SecurityCode Moduléo (vides acceptés : la VM démarre sans outils Moduléo) ; les **chiffre elle-même** avec la clé maître et n’écrit que les valeurs chiffrées ; aucune valeur en clair sur disque ;
   - crée le **premier compte administrateur** (`creer-admin`, interactif ; refuse s’il existe déjà un administrateur) ;
   - pose le service systemd et les timers des tâches planifiées.
   Commande `configurer-secret <env> <VARIABLE>` pour changer une clé plus tard (même chiffrement).
8. **Base de données** : mécanisme actuel conservé (`create_all` + ajouts de colonnes de `database.py`, ADR-0008) — pas d’Alembic. **Sauvegarde `pg_dump` avant chaque changement de version**, 5 dernières gardées par Environnement. Restauration **manuelle** documentée (`restaurer <env> <fichier>`), jamais automatique.
9. **Tâches planifiées — convention unique** : une tâche = une sous-commande de l’image (`tache <nom>`), déclarée par une ligne `<nom> <OnCalendar systemd>` dans `taches-planifiees.conf` (livré dans l’image). `installer` et `mettre-a-jour` génèrent un timer `bbass-<env>-<nom>.timer` par tâche et par Environnement, et retirent les timers qui ne sont plus déclarés. Seule tâche en 1.6.1 : **`purger-cache-pages`, toutes les heures**. Journal : `journalctl -u bbass-<env>-<nom>`.
10. **`GET /sante`** (sans authentification) : 200 `{"statut": "ok", "version": "X.Y.Z"}` si le serveur tourne et que Postgres répond, 503 sinon. Ne vérifie ni Mistral, ni Moduléo, ni SearXNG.
11. **CI** : nouveau compartiment **`build-image-vm`** (path filter + skip→vert, ADR-0020) sur les PR : build des deux images, démarrage de la stack de production, `GET /sante` → 200. Faux secret Mistral chiffré généré à la volée, Moduléo vide. Ajouté aux checks requis du ruleset `main` (geste humain, guide dans l’ADR). Workflow de publication sur Release + workflow manuel de promotion.
12. **Docs** : **ADR-0021** (CD de la VM) ; glossaire **Environnement**, **Promotion** ; guide admin sur le site de doc **« Installer et mettre à jour la VM centrale »** pour un admin du cabinet sans connaissance du code (prérequis Ubuntu/Docker, Ubuntu Pro via un compte Ubuntu One **au nom du cabinet** avec double authentification, installation, mise à jour, promotion, retour arrière, restauration, journal des tâches).

## User Stories

1. En tant qu’admin du cabinet, je veux installer la VM centrale sur une VM Ubuntu avec une seule commande, sans cloner le dépôt, afin de ne pas dépendre de l’alternant.
2. En tant qu’admin du cabinet, je veux que l’installation me demande les clés API en clair et les chiffre elle-même, afin de ne jamais manipuler de clé maître ni de script de chiffrement.
3. En tant qu’admin du cabinet, je veux que les mots de passe internes et la clé d’administration VM soient générés et affichés une seule fois, afin de les ranger dans le gestionnaire de mots de passe du cabinet.
4. En tant qu’admin du cabinet, je veux créer le premier compte administrateur pendant l’installation, afin que la production n’ait jamais de compte de test au mot de passe connu.
5. En tant qu’admin du cabinet, je veux mettre à jour la VM en lançant une commande ou en la redémarrant, afin de ne rien télécharger ni copier à la main.
6. En tant qu’admin du cabinet, je veux qu’une version qui ne démarre pas soit automatiquement remplacée par la précédente, afin que les collaborateurs gardent un chat qui marche.
7. En tant qu’admin du cabinet, je veux une sauvegarde de la base avant chaque changement de version et une commande documentée pour la restaurer, afin de revenir à l’état exact d’avant une mise à jour ratée.
8. En tant que développeur, je veux qu’une Release arrive automatiquement sur le staging, afin d’y jouer les tests humains avant les collaborateurs.
9. En tant que développeur, je veux promouvoir en prod exactement les images testées en staging, par un workflow manuel tracé, afin de choisir l’heure de bascule et de pouvoir revenir en arrière.
10. En tant que développeur, je veux que la promotion refuse une version jamais passée par le staging, afin qu’aucune version non essayée n’arrive en prod.
11. En tant que développeur, je veux que le staging lise le serveur de test Moduléo, afin de ne jamais essayer une nouveauté sur les données de production.
12. En tant que responsable sécurité, je veux que seul le port de la VM soit exposé sur le LAN et que chaque Environnement ait sa propre clé maître, afin qu’une fuite du staging n’ouvre pas la prod.
13. En tant que compte administrateur, je veux que le cache des pages web expirées soit purgé toutes les heures, afin que la base ne grossisse pas indéfiniment.
14. En tant que développeur, je veux une seule convention pour les tâches planifiées, afin d’en ajouter une sans toucher à la VM à la main.
15. En tant que développeur, je veux que chaque PR qui touche la VM prouve que l’image démarre et répond sur `/sante`, afin qu’une image cassée n’arrive jamais sur `main`.
16. En tant qu’admin du cabinet, je veux un guide d’installation et de mise à jour écrit pour moi, afin de reprendre l’exploitation sans connaissance du code.
17. En tant que développeur, je veux que le lancement de dev (`lancer-vm.*`) reste inchangé, afin que la 1.6.1 ne casse pas mon poste de travail.

## Implementation Decisions

- **Machine :** Ubuntu Server 26.04 LTS + Docker Engine (dépôt officiel Docker) + plugin Compose. La VM elle-même n’est pas livrée par cette version.
- **Packaging :** Compose de production distinct du `docker-compose.yml` de dev ; nom de projet Compose `bbass-<env>`.
- **Images :** GHCR, publiques (dépôt public, aucun secret dedans), tag `vX.Y.Z` + étiquettes mobiles `staging` / `prod` posées par retag (pas de rebuild).
- **Image `vm-centrale` :** point d’entrée qui expose les sous-commandes d’exploitation (`serveur`, `installer`, `mettre-a-jour`, `creer-admin`, `configurer-secret`, `restaurer`, `tache <nom>`). Les scripts de dev du dépôt (`seed_compte_test.py`, `affecter_groupes_moduleo.py`, essais réels Moduléo) n’en font pas partie.
- **Secrets :** format actuel conservé (Fernet, `VM_CLE_MAITRE_FICHIER`, ADR-0017/0018) ; seul le geste change (chiffrement fait par `installer` / `configurer-secret`).
- **Retour arrière :** automatique pour les images ; restauration de la base toujours manuelle (ne pas écraser des messages écrits entre-temps).
- **Pas d’Alembic** tant qu’aucune version ne renomme ou ne supprime une colonne (entrée Plus tard avec ce déclencheur).
- **Tâches planifiées :** systemd timers générés depuis `taches-planifiees.conf` ; pas de cron, pas de conteneur dédié.
- **Feuille de route (`/afr` sur la branche 1.6.1) :** 1.7.2 documentation complète de la base (schéma visualisé, toutes les tables) ; 1.7.3 relations entre les services ; Plus tard : Alembic, HTTPS LAN, sauvegarde nocturne + copie hors VM (NAS) + fichiers de pièces jointes, pull automatique / runner de déploiement à Castries, **Mise en production définitive** (checklist : Ubuntu Pro rattaché à un compte Ubuntu One du cabinet avec double authentification, secrets dans le gestionnaire du cabinet…).

## Testing Decisions

- **pytest HTTP-boundary (vm-centrale)** : `GET /sante` (200 avec base joignable, 503 sinon) ; `creer-admin` (crée, refuse s’il existe un administrateur) ; chiffrement fait par `configurer-secret` relu par `config.py` ; génération des timers depuis `taches-planifiees.conf` (ajout, retrait) ; rotation des sauvegardes (5 gardées) ; décision de la séquence de mise à jour (version inchangée → pas de sauvegarde ; `/sante` KO → retour aux images précédentes ; pas d’Internet → images présentes) testée sur sa logique, Docker simulé.
- **CI `build-image-vm`** : build des images + stack de prod démarrée + `/sante` 200 sur chaque PR qui touche la VM.
- **Tests humains** (VM Ubuntu 26.04 réelle ou de test) : installation staging puis prod ; Release → staging à jour après `mettre-a-jour` et après redémarrage ; promotion → prod ; promotion refusée pour une version jamais en staging ; version volontairement cassée → retour automatique ; restauration d’une sauvegarde ; purge horaire visible dans le journal ; seul le port de la VM joignable depuis un poste du LAN ; un poste se connecte à la prod (8000) et au staging (8001).

## Out of Scope

- Packaging et installateur des **postes** (→ 1.6.2).
- CI des versions (→ 1.6.0, inchangée sauf ajout du compartiment `build-image-vm`).
- Écriture Moduléo (→ 1.5.2).
- Alembic, HTTPS sur le LAN, sauvegarde nocturne et copie hors VM, sauvegarde des fichiers de pièces jointes, pull automatique ou runner de déploiement à Castries (→ Plus tard).
- Fournir ou configurer la VM Ubuntu elle-même, l’activation effective d’Ubuntu Pro (geste humain, guide seulement).
- Satellites et exposition Internet (ADR-0003).
