# Dépendances Python gérées par uv, avec uv.lock committé

`vm-centrale/pyproject.toml` et `poste/pyproject.toml` ne fixaient que des bornes basses (`fastapi>=0.115`, etc.), sans fichier de verrouillage. `pip install -e .`, appelé par `scripts/preparer-package.bat`/`.sh` à chaque premier lancement d'un poste, résolvait donc des versions différentes selon la machine et la date d'installation — signalé par SonarCloud (`text:S8565`, MAJOR, sur les deux `pyproject.toml`) comme un risque réel, pas un faux positif : deux postes installés à des dates différentes peuvent légitimement finir sur des versions de dépendances différentes, y compris avec des correctifs de sécurité divergents.

Bascule sur **uv** comme gestionnaire de dépendances pour les deux packages Python (`vm-centrale`, `poste`) : `uv.lock` committé dans chacun fige les versions exactes résolues (dépendances directes et transitives), `.python-version` (`3.11`) fige l'interpréteur — nécessaire en pratique : sans lui, `uv sync` a sélectionné un Python 3.13 présent sur la machine plutôt que le 3.11 attendu, silencieusement. `requires-python` resserré à `>=3.11,<3.12` dans les deux `pyproject.toml` pour que cette contrainte, déjà documentée dans le README (Prérequis), soit aussi portée par l'outillage.

## Consequences

- `scripts/preparer-package.bat`/`.sh` appellent désormais `uv sync --extra test --python 3.11 --locked` au lieu de `python -m venv` + `pip install -e .` ; `--locked` fait échouer la commande si `uv.lock` n'est plus synchronisé avec son `pyproject.toml`, plutôt que de re-résoudre silencieusement. Rien en aval ne change : le résultat reste un `.venv` standard (`Scripts/python.exe` / `bin/python`), donc `lancer-vm.bat`/`.command`, `lancer-logiciel.bat`/`.command` et `scripts/ouvrir-fenetre-mac.sh` sont inchangés.
- **uv n'est pas un prérequis manuel** (README, section Prérequis : Python 3.11 et Docker Desktop seulement). Contrairement au front (ADR-0010, où le `dist/` compilé est committé et Node.js n'est donc jamais nécessaire à l'exécution), les dépendances Python de `vm-centrale` et `poste` sont installées localement à chaque premier lancement — c'était déjà le cas avec `pip install -e .`, uv ne fait que remplacer cette étape par une version reproductible. Les lanceurs (`scripts/verifier-uv.bat` / `.sh`, appelés depuis `preparer-package`) installent uv via le script officiel Astral s'il n'est pas déjà présent.
- Faire évoluer une dépendance passe désormais par `uv add`/`uv lock` (qui met à jour `uv.lock`) plutôt qu'éditer `pyproject.toml` à la main puis réinstaller : un `pyproject.toml` modifié sans relancer `uv lock` fait échouer `uv sync --locked` sur le prochain poste qui se prépare, au lieu de dériver silencieusement.
- `scripts/verifier-python.bat`/`.sh` reste inchangé (garde-fou rapide et pédagogique si aucun Python 3.11 n'est présent) ; `uv sync --python 3.11` réutilise ensuite le même interpréteur.
