# Front du poste en React/TypeScript/Vite, build committé dans git

À partir de la [1.2.0](../specs/v1.2.0-interface-poste.md), le front du poste (`poste/src/poste/static/`) cesse d'être du HTML/CSS/JavaScript nu écrit à la main pour devenir une application React/TypeScript, buildée par Vite, avec shadcn/ui (composants copiés dans le repo, pas une dépendance opaque) et Tailwind CSS pour le style, TanStack Query pour les appels à la VM centrale. Aucun routeur : la navigation entre écrans reste un état interne, sans URL, cohérent avec une appli locale mono-fenêtre (LAN, futur lanceur pywebview).

Ce choix part d'une contrainte à venir plutôt que d'un problème déjà bloquant aujourd'hui : à terme, plus aucune personne qualifiée ne sera sur place pour faire évoluer le logiciel elle-même — c'est un agent IA de développement qui continuera cette évolution, un compte administrateur se contentant de valider les changements (voir la feuille de route, section « Agent IA de continuation du développement »). Un unique fichier JavaScript nu, déjà à 1277 lignes en 1.1.3 et voué à grossir avec chaque nouvel écran (1.3.0 Agent Moduléo, 1.4.0 pièces jointes, futurs Agents et pôles), est le pire terrain pour un mainteneur qui n'est ni humain ni relu par un humain technique : TypeScript offre un filet à la compilation qui remplace en partie cette relecture absente, et un découpage en composants React limite la casse quand l'agent IA modifie un écran sans en comprendre tous les voisins.

**Aucune étape de build sur le poste, jamais.** Il n'existe aujourd'hui aucune CI (`.github/workflows/` absent) et l'installation d'un poste est « `git clone` + `pip install -e` », sans étape de build ; les fichiers `static/` sont committés tels quels et lus directement par FastAPI (`StaticFiles`/`FileResponse`, `main.py`). Introduire Node.js comme dépendance d'exécution sur un poste — une machine collaborateur, sans personne qualifiée pour la maintenir — contredirait directement [ADR-0001](0001-backend-local-par-poste.md). Le dossier compilé par Vite (`dist/`, redirigé vers `poste/src/poste/static/` via `build.outDir`) est donc committé dans git exactement comme les fichiers actuels : `npm run build` ne tourne jamais sur un poste, seulement sur la machine (ou par l'agent IA de dev) qui prépare un commit. Une CI/CD qui prendrait en charge ce build à la place d'un commit direct du `dist/` est une évolution déjà notée dans la feuille de route, non construite ici.

## Consequences

- `poste/frontend/` (source React/TypeScript/Vite, son propre `package.json`) n'est jamais installé ni buildé en production — uniquement au moment de préparer un commit. Tout code qui suppose Node.js disponible sur un poste au runtime est un bug.
- `poste/src/poste/static/` change de nature : ce n'est plus du code source édité à la main, mais un artefact généré par `vite build`, committé tel quel. Un futur mainteneur (humain ou agent IA) qui voudrait modifier l'interface édite `poste/frontend/`, jamais directement les fichiers sous `static/` — ceux-ci seront écrasés au prochain build.
- `poste/pyproject.toml` et `main.py` (`_STATIC_DIR`, `StaticFiles`, `FileResponse`) n'ont pas à changer : le wheel continue d'embarquer `static/` comme aujourd'hui, que son contenu soit écrit à la main ou généré.
- Pas de test automatisé de composant React introduit par ce choix (cohérent avec `CLAUDE.md` : tests HTTP-boundary uniquement) — un filet de sécurité UI (Playwright) reste une évolution future, non couverte par cette ADR.
- Cette ADR ne remet pas en cause [ADR-0001](0001-backend-local-par-poste.md) (backend et interface web toujours installés et exécutés localement par poste) : elle en précise seulement la conséquence pour l'outillage frontend, dans un contexte où la maintenance humaine directe du code n'est plus garantie.
